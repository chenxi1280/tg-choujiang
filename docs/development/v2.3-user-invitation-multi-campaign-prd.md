# TG 群抽奖机器人 V2.3 用户邀请与同群多活动整体 PRD

状态：本地实现与自动化验证完成；部署和真实 Telegram E2E 未执行

日期：2026-08-19

实现说明：当前代码已落地同群并行活动、逐活动逐群稳定邀请入口、底层链接版本、截止后继续入群、群级成员历史、按活动参与/邀请记录和权限提醒。自动化结果只证明本地代码与测试数据库行为，不等同于生产发布或真实 Telegram 客户端验收。

适用范围：V2.3 新建活动。V2.1/V2.2 已发布活动继续执行其冻结合同；本文明确覆盖 V2.2 的“同群独占”“链接随截止失效”和参与者记录部分。

## 1. 一页结论

| 用户问题 | V2.3 产品结论 |
|---|---|
| 邀请加成从哪里获取 | 在“我的加成 → 邀请加成”获取逐群链接；有效人数达到该群门槛后自动写入抽奖次数，无需手动领取 |
| 每个群是否不同 | 是。每个参与群独立设置规则、生成链接、累计人数、计算上限和展示记录 |
| 每次抽奖链接是否不同 | 是。外发邀请入口唯一绑定“活动 × 邀请人 × 参与群”，任何两个维度不同都不是同一链接 |
| 同一群能否有多个抽奖 | 能。活动卡、回调、链接、报名、消息加成、邀请归因和票账本全部按活动隔离 |
| 抽奖截止后链接能否入群 | 能。截止只关闭本期归因和计票，默认不关闭入群；页面明确显示“仅入群，不再计算本期加成” |
| 邀请记录在哪里看 | 私聊首页“我的邀请记录”，或某次活动的“邀请加成 → 某群 → 邀请记录” |
| 参与记录在哪里看 | 私聊首页“我参加的抽奖”，按进行中/待开奖/已结束分类，点击查看资格、票数、加成和结果 |

核心身份定义：

~~~
PersonalReferral = Campaign × Participant × ParticipationGroup
~~~

它不是“用户的全局邀请链接”，也不是“某个群的永久奖励链接”。旧活动链接永远不能给新活动加成。

## 2. 设计目标与非目标

### 2.1 目标

- 用户始终知道自己正在操作哪一次抽奖、哪一个群，以及当前操作是否还能获得加成。
- 同群多活动并行时不串活动、不串邀请人、不串群、不串票。
- 截止、开奖、归档和入群能力解耦。
- 邀请人能看到可解释、可追溯、保护隐私的邀请与参与记录。
- Telegram 权限、链接创建、入群观察或资格核验失败时显示真实状态和恢复动作。

### 2.2 非目标

- 不把“点击邀请入口”当作有效邀请；只有可核验的新成员入群事实才可能计奖。
- 不保证机器人能识别其加入目标群之前的完整历史成员关系。
- 不在 V2.3 增加并发活动数、邀请数或链接数的任意产品上限；远端明确拒绝时如实报错。
- 不允许活动发布后追溯修改逐群邀请/发言规则。

## 3. 统一对象与两层链接

### 3.1 五个业务对象

| 对象 | 责任 |
|---|---|
| Campaign | 一次具体抽奖，拥有公共短编号、时区、报名截止、开奖时间和冻结规则 |
| ParticipationGroup | 本次抽奖的一个参与群；同一 Telegram 群可同时属于多个 Campaign |
| Participant | 某用户在某 Campaign 下的参与身份 |
| ReferralRoute | 对外可复制、可转发的本期邀请入口，稳定绑定 Campaign、Participant、ParticipationGroup |
| TelegramInviteLinkVersion | 真正执行入群的 Telegram 邀请链接，可因撤销或远端故障轮换版本 |

所有页面都显示“活动名 + 短编号 + 开奖时间”。同名活动不能只显示名称；同名群显示标题加 username，无 username 时显示 chat ID 尾号。

### 3.2 为什么拆成两层链接

邀请人复制的是稳定入口：

~~~
https://t.me/{bot_username}?start=ref_{opaque_ref}
~~~

打开后先进入活动邀请落地页，再点击“加入 A 群”。落地页根据当前状态展示活动信息、目标群、加成期限和入群按钮。它的好处是：

- 链接本身能明确区分每次抽奖、邀请人和群。
- 截止后无需换链接，页面可切换成“只入群、不计加成”。
- Telegram 底层链接被撤销并轮换时，已外发的稳定入口仍可指向新版本。
- 邀请人不需要理解或保管一组会变化的 Telegram 原始链接。

底层 Telegram 链接也必须唯一映射到一个 ReferralRoute；其名称使用中性随机值，不放用户 ID、昵称或活动隐私。

受邀人打开稳定入口后，机器人可用当前用户身份检查目标群成员状态。明确已在群内时立即提示“已是成员，不会产生邀请加成”，并为邀请人留下不计奖原因；核验 UNKNOWN 时不下结论。打开入口本身仍不产生抽奖次数。

### 3.3 两类入群入口

| 入口 | 是否绑定邀请人 | 是否产生邀请归因 | 用途 |
|---|---:|---:|---|
| 个人本期邀请入口 | 是 | 满足规则时是 | 邀请人分享、查看进度 |
| 活动普通入群入口 | 否 | 否 | 报名补群、截止后正常入群、个人链接不可用时的安全回退 |

“立即参与”是活动报名入口，不是邀请加成链接。用户通过普通群 username、搜索或普通入群入口加入时，不给任何邀请人归因。

## 4. 时间语义：截止不等于链接失效

每次活动明确展示三个时间：

| 时间 | 含义 |
|---|---|
| 报名/抽奖截止时间 | 不再接受本期报名和新增计票事实 |
| 邀请加成最晚入群时间 | 截止时间减去最低留存时长；超过后即使入群也来不及完成本期留存 |
| 链接可入群期限 | V2.3 默认长期可用，不因截止、开奖或归档自动过期 |

所有判断使用 Campaign 冻结时区和 Telegram 事件时间；页面同时显示时区，不能使用 worker 接收时间或服务器本地时区替代业务截止。

状态计算：

~~~
bonus_join_deadline = campaign_cutoff_at - retention_duration

event_at <= bonus_join_deadline  -> 可创建本期邀请候选
event_at >  bonus_join_deadline  -> 仅入群，不创建本期奖励候选
~~~

候选在最晚入群时间前产生后，可以在留存期结束时完成核验；开奖必须等待截止前候选收敛为确认、明确无效或 UNKNOWN 阻断，不能把任务延迟当作用户无效。

链接生命周期：

| 活动状态 | 外发入口 | 入群 | 本期归因 |
|---|---|---:|---:|
| 进行中且未过最晚入群时间 | 正常邀请页 | 是 | 是 |
| 进行中但已过最晚入群时间 | “仍可入群，本期已来不及获得加成” | 是 | 否 |
| 已截止/待开奖/已开奖/已归档 | “本期已结束，仅用于入群” | 是 | 否 |
| 活动取消 | 显示活动已取消，转为普通入群入口 | 视群状态 | 否 |
| 群或链接被明确撤销 | 显示不可用原因；公开群提供 username，私有群等待修复 | 视回退能力 | 否 |

截止、开奖、归档不再自动撤销个人链接，也不再把 Telegram expire_date 设置为截止时间。取消活动、安全处置或群管理员明确撤销是独立动作。

## 5. 同一群多个抽奖

### 5.1 创建者体验

群选择页不再出现阻断选择的“已有未结束活动”。改为可选择提示：

~~~
☑ A 群
当前另有 2 个进行中抽奖
[查看并行活动]
~~~

发布确认页列出重叠活动的名称、短编号和时间，只做明确提醒，不静默替创建者选活动，也不引入并发数量上限。

活动详情在截止后显示“本活动链接继续可入群”。当前群管理员可以显式执行“停止本活动链接入群”，操作前二次确认影响的群和活动；该动作只撤销本活动链接，不删除成员、邀请记录或票账本。

### 5.2 群内展示

每个活动拥有独立活动卡：

~~~
🎁 八月会员抽奖 #7K3M2Q
截止：08-25 20:00
开奖：08-25 20:10

[立即参与本次抽奖]
[参与条件] [我的加成]
~~~

群内通用命令或按钮若没有 Campaign 上下文：

- 只有一个可操作活动时可以直接进入。
- 有多个活动时必须先展示活动选择器。
- 不得按“最新创建”“最近截止”或数据库返回第一条隐式选择。

### 5.3 参与、消息与邀请隔离

- 同一用户可同时参加 A 群里的 Campaign 1 和 Campaign 2，形成两个 Participant。
- 同一条 A 群消息，如果用户分别参加两个活动且同时满足两套冻结规则，可各自在两个活动中计数；它是一个远端消息事实向多个活动投影，不是重复伪造消息。
- A 群的 Campaign 1 邀请链接只影响 Campaign 1；Campaign 2 必须生成另一条本期入口。
- 加入事件使用 Telegram 实际返回的底层 invite link 精确定位唯一活动、邀请人和群。
- 用户在同一群只能成为一次“首次观察到的新成员”。退群后通过另一个活动链接重新加入，不能再次作为新成员获奖。

### 5.4 同一受邀人跨活动冲突

群级成员历史使用稳定键：

~~~
GroupMembershipFact = Group × TelegramUser
~~~

首次可确认的新成员事件原子写入该事实。后续任何活动看到该用户重新加入时，邀请记录显示“已是/曾是本群成员”，不计加成。

若两个活动几乎同时收到同一用户的加入更新，由数据库唯一约束和事务锁确定唯一首次事实；只有 Telegram 事件实际携带的那条链接拥有归因候选。不能一人同时给同一群的两个活动加成。

同一个受邀人加入 A 群和 B 群是两个不同成员事实，因此在两个群都确为新成员且分别使用对应链接时，可以各计一次逐群邀请。

## 6. 参与者按钮与记录交互合同

私聊首页、我参加的抽奖、我的邀请记录、逐群邀请详情、受邀人落地页、截止前后按钮、分页、空态和失败恢复统一执行 [V2.3 按钮与记录交互合同](v2.3-participant-button-record-interaction-contract.md)。

强制入口为：

- 群活动卡“我的加成”进入该 Campaign 的私聊页面；
- 私聊首页常驻“我参加的抽奖”和“我的邀请记录”；
- 活动详情可进入加成、票数明细、参与条件和结果；
- 单群邀请详情可复制/转发本期入口并查看该活动该群的邀请记录。

任何页面不得隐式选择“最近活动”，也不得在截止后隐藏可用入群入口。

## 7. 邀请归因与计票规则

生成入口和达到人数都不需要用户再点“领取”。一次邀请成为有效记录必须同时满足：

1. 底层 Telegram invite link 能精确解析到唯一 ReferralRoute。
2. 实际加入群等于 ReferralRoute 的 ParticipationGroup。
3. 受邀人不是邀请人本人，也不是机器人。
4. 群级历史中没有该用户已是/曾是成员的确认事实。
5. 加入事件不晚于本期最晚计奖入群时间。
6. 完成最低留存，并在截止前没有退群。
7. 远端事实为确认；UNKNOWN 保持待处理，不自动按通过或失败处理。

落地页已确认受邀人当前在群内时，可以生成 existing_member 不计奖记录，帮助邀请人理解原因；它不是入群事实，也不能增加有效人数。

转发别人的链接不会改变归因，始终归属于该链接的 Participant。用户先后打开多个链接时，只认最终 Telegram 入群事件实际携带的链接，不使用“最后点击”或 Cookie 猜测。

逐群公式继续独立：

~~~
raw_target(campaign, participant, group)
  = floor(valid_invites / invites_per_cycle)

group_target = raw_target                         // 不限
group_target = min(raw_target, max_bonus_tickets) // 有限

campaign_invite_tickets = sum(group_target)
~~~

有效后在截止前退群，只冲正该 Campaign、Participant、ParticipationGroup 的目标差额；截止快照冻结后再退群不改写本期历史结果。

## 8. 逐群发言与多活动

V2.2 的逐群独立规则继续保留。多活动新增以下明确语义：

- 消息事实先按 Telegram chat_id、message_id、user_id 去重，再分别投影到符合时间、资格和群规则的 Campaign。
- 用户只参加 Campaign 1 时，消息不能进入 Campaign 2。
- 两个活动的最低字数、每轮条数、每日上限和活动时区分别冻结并分别计算。
- 用户页面必须从具体活动进入，不能把多个活动的“今日发言次数”相加成一个全局数字。
- 同一活动内 A、B 群仍分别计算，A 群消息不会补 B 群进度。

## 9. 权限、提醒与恢复

### 9.1 创建与发布

- 群选择页常驻“先把机器人加入群并设为管理员”的引导。
- 每个群逐行显示机器人未入群、不是管理员或缺少创建邀请链接/发送消息/观察成员等具体权限。
- 同群存在其他活动只提示，不作为权限失败。
- 发布前一次列出全部失败群；任何群失败都不能显示“全部发布成功”。

### 9.2 运行期

- 机器人被移除、降权或失去创建链接权限时，为每个受影响 Campaign 建立运营阻断。
- 创建者提醒按“群 + 权限状态”去重合并，可显示“该群影响 3 个活动”，进入后逐活动查看。
- 邀请人打开详情时看到具体群、失败原因和“重新检测”，其他正常群仍可独立使用。
- 受邀人落地页若私有群链接暂不可用，显示“暂时无法生成入群能力”，不得给假 URL；公开群可显式提供 username 回退。
- Telegram 返回结果未知时进入 UNKNOWN_HOLD，只能查询/对账后决定是否轮换，不能盲目重复创建链接。

### 9.3 链接轮换

运行中底层链接明确被撤销或明确创建失败时，可以为同一 ReferralRoute 创建新版本：

- 同一时刻只能有一个 current 版本。
- 旧版本保留 hash、时间和撤销原因用于审计。
- 外发稳定入口不变，自动指向 current 版本。
- 轮换不改变 Campaign、邀请人、群或既有邀请记录。

## 10. 数据与实现合同

### 10.1 参与群并行

- 删除 campaign_participation_groups 上“group_id 在未释放活动中唯一”的约束。
- 保留“同一 Campaign 不能重复选择同一 Group”。
- 增加适合按 Group 查询多个活动的普通索引。
- active_campaign_by_chat 改为 active_campaigns_by_chat；所有无活动上下文的调用必须处理 0/1/N。
- 发布、成员变化、消息投影和权限阻断都必须遍历明确活动集合，不得取第一条。

### 10.2 稳定邀请入口

新增 campaign_referral_routes 或等价一等模型：

| 字段 | 约束 |
|---|---|
| public_ref | 全局唯一、随机、不可枚举 |
| campaign_id | 必填 |
| participant_id | 必填 |
| participation_group_id | 必填 |
| bonus_join_deadline | 冻结时间 |
| status | active / join_only / cancelled / blocked |

唯一键为 Campaign、Participant、ParticipationGroup。

底层 telegram_invite_link_versions 至少包含 route_id、version、link_hash、encrypted_url、remote_created_at、telegram_expire_at、is_current、revoked_at、revoked_reason 和 delivery certainty。telegram_expire_at 对 V2.3 正常链接为空。

### 10.3 群级成员事实

新增 group_membership_facts 或等价模型：

| 字段 | 含义 |
|---|---|
| group_id + user_id | 唯一键 |
| first_observed_member_at | 首次确认成为成员 |
| first_source_link_version_id | 可空；首次来源 |
| last_observed_state | member / left / unknown |
| last_observed_at | 最近观察时间 |
| certainty | confirmed / unknown |

旧数据只能从已有确认事件构建“机器人已观察事实”，不能声称覆盖机器人加入前的成员历史。

### 10.4 邀请、记录和账本

- Invitation 继续唯一到 Campaign、ParticipationGroup、invitee_user_id，并关联 route 和实际 link version。
- 增加稳定 final_reason、截止快照状态和必要的脱敏显示快照。
- TicketLedger 业务键继续包含 Campaign、Participant、ParticipationGroup 和目标档位。
- 参与记录查询必须接受 user_id + campaign_public_ref；禁止“默认最近一个活动”。
- 邀请记录查询必须接受 user_id + campaign_public_ref + participation_group_ref，并分页返回状态、原因和时间。
- 任何汇总都从确认事实与票账本读取，不能用页面缓存反推。

## 11. 兼容与迁移

1. 为新活动写入 contract_version=2.3；已发布旧活动不改规则、不回填票、不重算邀请。
2. 先完成所有 0/1/N 活动查询和事件投影，再删除同群独占索引；顺序反过来会产生隐式串活动。
3. V2.2 旧个人链接若已设置 Telegram 过期时间，不宣称能够复活。历史页显示真实“旧版链接已过期”，有普通入群入口时提供回退。
4. V2.3 新链接不设置截止过期时间；截止任务只冻结归因、结算账本和切换页面状态。
5. 旧草稿涉及同群独占、链接过期或逐群邀请时，恢复后要求创建者重新确认 V2.3 合同，不能静默升级。
6. 已有 Invitation 仅迁移已有 Campaign/Participant/Group 关系，不伪造群级首次成员历史。
7. 回滚必须保留已经产生的 V2.3 路由、链接版本、邀请和票账本；旧代码若不能处理同群多活动，不得直接回滚上线。

## 12. 关键异常与遗漏补齐

- 加入申请：申请只显示“等待管理员批准”，批准并真实入群后才开始留存。
- 已在群内：点击链接可以打开群，但不产生新成员奖励。
- 退群重进：群级历史阻止跨活动重复算新成员。
- 私聊被阻止：群活动卡继续提供 bot deep link；用户恢复私聊后可回到同一 Campaign 页面。
- 同名活动/同名群：始终带短编号和稳定群标识。
- 活动改名：路由和记录按稳定 ID，不按名称匹配；记录保留发生时标题快照。
- 群迁移：使用稳定 Group 关系迁移 chat_id，不把新 chat_id 当新群重复计奖。
- 删除账号：历史记录保留脱敏标识和账本事实，不因 Telegram 资料不可查而删除票。
- 链接泄漏：获得链接的人可继续转发，但奖励仍归原 Participant；创建者和邀请人页面明确提示。
- 延迟 Update：使用 Telegram 事件时间判断截止，使用接收时间做审计；不能因 worker 延迟误判。
- 并发/重放：Update、入群事实、路由创建、版本轮换和票据目标都必须幂等。
- 活动取消：不再计奖；个人底层链接可撤销，但落地页在权限允许时切换为普通入群。
- 多活动通知：同一群权限故障合并提醒，业务阻断仍逐 Campaign 留痕，避免刷屏同时保留责任边界。
