# TG 群抽奖机器人 V1.9 创建预览与抽奖加成 PRD

状态：开发合同

日期：2026-08-14

上游合同：V1.8 LotteryBestBot 修复 PRD

## 1. 目标与边界

本版本把创建入口统一为“先看到完整抽奖预览，再逐项设置”，并把旧“人品加成”替换为可配置、可审计的“抽奖加成”。开奖仍只消费冻结的追加式票账本与不可变快照，不改变 `sha256-weighted-v2`、多奖品顺位和唯一中奖人规则。

历史已发布活动不改规则、不回填、不重算票账本。旧规则缺少 `bonus_types` 时，仅为继续执行该冻结活动而按旧 `luck_mode` 解释；所有新活动必须显式冻结加成类型和参数。

## 2. 创建与预览

点击“创建/继续抽奖”或发送 `/new`：

1. 有有效草稿时恢复同一草稿并显示预览。
2. 无草稿时立即创建空草稿并显示预览，不先要求奖品名称。
3. 只有一个可管理活动群时自动绑定；有多个活动群时预览显示“活动群”入口供选择。
4. 标题、封面、用户限制、参与条件、奖品、说明、抽奖加成、开奖方式、发奖人员和消息提示都从预览按钮进入。
5. 发布时仍统一校验活动群、标题、至少一个奖品和开奖条件；未满足时保留草稿并明确列出缺失字段。

清空草稿后也返回全新预览，不重新进入强制向导。

## 3. 参与条件

活动主群始终是参与条件，添加页必须明确说明无需重复添加；创建者再次输入主活动群时返回专门提示，不得混入普通“条件重复”错误。创建者可以额外配置任意数量的群聊或频道，也可一次输入多个值。主操作是直接发送 `https://t.me/<username>` 公开链接或 `t.me/c/<内部群号>/<消息号>` 私有消息链接；`@username` 和数字 chat ID 仅作为兼容/高级方式，界面不得把 chat ID 称为“用户 ID”。

Telegram 的 `t.me/+...` 或 `joinchat` 邀请哈希不能由 Bot API 反查群/频道身份，系统必须明确拒绝；若它属于主活动群则无需添加，否则提示创建者发送 `t.me/c/...` 消息链接或转发来源可见的频道消息，不能猜测、静默跳过或把邀请哈希当作用户名。转发消息只有在 Bot API 明确携带群聊/频道来源时才能作为权威标识；来源隐藏或只携带原作者身份时必须明确要求改发消息链接。

参与条件列表必须提供明确的“添加参与条件”入口。点击后进入独立输入提示页，说明支持的标识和分隔方式，并提供返回条件列表的按钮；不能用刷新相同列表来暗示用户直接回复。

每项在加入草稿时由 Telegram 解析并验证 Bot 管理权限，按实际 chat ID 去重；发布前重新解析并冻结 chat ID、标题、类型、公开用户名/私有状态和加入路径。`getChat` 可访问性失败必须指出原输入目标，`getChatMember` 或管理员状态失败必须指出已解析群/频道标题和所需动作；Telegram API 原始异常只进日志，不回显给用户。公开条件已有稳定加入链接，不要求创建私有邀请链接权限；私有条件必须额外验证 Bot 的邀请用户权限。频道对用户展示“关注频道”，群组展示“加入群聊”。

本版本不设固定 2 个、3 个或 10 个的产品数量上限。若未来因 Telegram 或业务约束需要上限，必须作为显式产品规则另行确认，不能静默截断。

为避免条件较多时撑爆 Telegram 消息或按钮，创建侧每页显示 10 项并支持翻页、按一个或多个全局编号精确删除及清空；正式活动卡只显示一个“查看参与条件”入口，私聊条件页逐项展示并支持上一项/下一项。资格核验必须覆盖全部冻结条件，并按每批 10 项并发观察；批大小只是 Telegram API 调度参数，不是产品数量上限，任何一项 `INELIGIBLE` 都不合格，只有无不合格项但存在 `UNKNOWN` 时保持待核验。

## 4. 抽奖加成

抽奖加成是额外抽奖次数。每增加 1 次，就向 `ticket_ledger` 追加对应权重；`Participant.ticket_total_cache` 只是账本缓存，不能由管理员直接编辑。

新草稿默认关闭抽奖加成。创建者可只开邀请、只开发言、同时开启或全部关闭。配置必须全部通过 Telegram 内联键盘完成，不要求创建者记忆或回复文本语法：加成首页负责启用/关闭和进入子设置；邀请页支持新增/删除最后一档以及人数、累计次数增减；发言页支持每日消息阈值和当日增加次数增减。每次点击即时保存草稿并重绘当前设置摘要。

### 4.1 邀请抽奖加成

邀请配置采用“累计有效邀请人数:累计增加次数”阶梯，并必须设置总上限。例如 `1:1,2:3 上限3` 表示：

- 第 1 个邀请满足活动冻结的入群、留存和资格规则后，邀请人累计获得 1 次加成；
- 第 2 个邀请有效后，邀请人的邀请加成累计应为 3 次，因此本次只补发 2 次；
- 未命中新阶梯时不新增次数；累计次数永不超过配置上限。

最后一档累计增加次数必须等于总上限，避免配置出永远无法达到的“名义上限”。

被邀请人不需要先完成抽奖报名，但必须由活动专属邀请链接完成首次归因。在留存到期时，被邀请人必须仍是主活动群以及全部冻结额外群/频道的成员；任一条件不满足均不生效，任一 Telegram 观察未知则保持待核验并重试。

邀请生效后，如果被邀请人在报名截止前退出任一必需群/频道，系统按当前有效邀请人数重新计算阶梯并向账本追加负数冲正。首次留存验证因缺少某一条件而失败时，后续补关注或补入群同样可以从本次加入时间重新计算完整留存期。重新加入不会改变首次邀请归因。报名截止后不再因成员变更重算邀请加成，结算继续使用截止边界冻结的权重事实。

退出事件由 Durable Update 实时处理；结算排空期必须处理所有 `event_at <= cutoff_at` 的成员变更后才能冻结权重。截止后调用 `getChatMember` 只能证明查询时的当前状态，不能反推截止时状态，因此不得把截止后的查询结果倒填为 `cutoff_at` 或据此冲正。邀请留存验证必须保存逐群/频道观察时间、状态和错误，便于审计具体失败条件。

每个合格参与者必须能从报名成功面板主动获取“本期专属邀请链接”；callback 必须携带活动公开引用，并用 Campaign、Participant 和点击用户三者联合校验，不能返回其他活动或其他参与者的链接。链接尚在异步创建时明确提示稍后重试，不伪造临时链接。

个人邀请链接按 `(campaign_id, participant_id)` 唯一，同一用户参与新活动时必须生成新链接。正常报名截止、开奖或归档后，旧链接仍可作为普通 Telegram 入群链接使用，但数据库只接受 `preheat_at <= event_at <= cutoff_at` 且活动处于可归因状态的事件，因此旧链接不会继续增加旧活动加成，也不能串入新活动。只有活动取消时撤销个人链接；额外私有参与条件的临时入口仍可在正常截止时撤销。

专属邀请链接、首次归因、自邀拒绝、Bot 拒绝、留存校验、截止边界和重放幂等继续沿用现有合同。Campaign 行锁串行化同活动的阶梯结算，账本业务键保证同一结算事实不会重复发放。

### 4.2 发言抽奖加成

发言配置采用“每日有效消息阈值:当日增加次数”。例如 `10:1` 表示参与者在活动时区的某个自然日达到 10 条有效消息后，当日增加 1 次抽奖机会。

每天单独结算：今天达标就发，明天未达标就不发，后天再次达标则再次发。规则不要求连续天数。同一天超过阈值后不重复结算；日期按 Campaign 冻结时区计算。

发言只统计主活动群，不汇总额外参与条件群。Telegram 频道没有普通成员发言语义，因此主活动载体为频道时禁止发布开启了发言加成的活动；创建者必须关闭发言加成或改选群聊作为主活动群。

有效消息去重、Bot/服务/转发排除、最小文本长度、截止时间和 Durable Update 语义继续沿用现有实现。每日结算按本次新增次数写一条差额账本，业务键包含 Campaign、用户、本地日期和结算目标；重放不会重复发放，也不会按奖励次数放大为大量账本行。

### 4.3 配置范围

创建输入和冻结规则必须执行相同范围，超出范围时明确拒绝，不得截断：每日有效消息阈值为 `1–10000`，每日发言增加次数为 `1–100`，单档邀请人数不超过 `100000`，邀请累计增加次数与总上限不超过 `10000`。同一份配置中“邀请”和“发言”各只能出现一次，零值在创建阶段立即拒绝。

只有开启邀请加成时才创建和发送专属邀请链接；只开发言或关闭全部加成时，报名成功文案不得承诺邀请链接。

## 5. 展示与验收

创建预览、规则页和正式活动卡统一使用“抽奖加成”。关闭时说明仅有基础抽奖机会；开启时显示邀请阶梯/上限与每日发言阈值/次数。
