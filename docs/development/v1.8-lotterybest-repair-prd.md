## 0. 结论与发布决策

当前实现不能称为完成 `@LotteryBestBot` 全功能对齐。现有 81 项自动化测试与 Ruff 均通过，但测试未走通“页面渲染 → 安全回调 → 创建处理器”的真实链路，也未覆盖运行中活动的多群开奖复核、满人并发触发、发布重试和 Telegram 客户端全按钮 E2E。

V1.8 将已确认差距转换为可开发、可迁移、可回归、可实机验收的修复合同。所有 P0 在合并、发布和宣称对齐前必须关闭；P1/P2 未关闭时只能按实际能力发布，不得继续使用“完整对标”结论。

唯一允许保留的核心差异是开奖内核：本项目继续使用追加式票账本、开奖前资格复核、不可变快照、多奖品顺位分配和 `sha256-weighted-v2`。交互、调度、参与资格、管理入口、消息语义、人品积分和可见业务能力不属于该豁免。

证据状态统一使用：

- `pass`：指定层级的验收已实际执行且有可复核证据；
- `blocked`：存在明确外部阻断，已记录阻断点与恢复条件；
- `unproven`：尚未执行或证据不足，不能由测试、CI、容器健康或接口健康替代。

### 0.1 已确认参考证据锚点

- 本轮 Telegram 实机满人开奖设置页明确显示：30 天仍未满时，在到期日中午 12:00 自动开奖；因此 R-P0-05 的“活动时区第 30 天 12:00”是已观察参考规则，不是推断值。
- 本轮 Telegram 实机消息提示页明确列出同步删除命令开关、10/20/30 秒、1/5/10/30/60 分钟和不删除；因此 R-P1-03 的档位是已观察参考菜单，不是默认猜测。
- 以上只证明参考 Bot 可见规则，不证明本项目已经实现；本项目对应自动化、数据库和 Telegram E2E 状态仍为 `unproven`。

## 1. 目标、范围与非目标

### 1.1 目标

- 创建者可按参考 Bot 的业务语言完成整个创建流程，所有页面按钮都可达、可返回、可恢复且不会误改新草稿。
- 报名和开奖使用同一组冻结参与条件；离开任一必加群/频道的用户不得进入开奖快照。
- 满人开奖在达到人数的事务边界内可靠触发，并在活动时区的第 30 天中午 12:00 执行兜底。
- “消息提示”恢复为参与完成提示的延迟删除能力；必要错误、开奖结果和发奖人员事实不受其影响。
- “人品加成”实现为独立积分与兑换票体系，而不是三个隐藏票规则预设。
- `/index`、活动详情、规则页、报名页、客户等级与导航/精选推送形成可操作闭环。
- 发布、回调、积分兑换、满人触发和资格冻结具备数据库级幂等、审计与失败恢复。

### 1.2 范围

本期覆盖一级命令、创建向导、创建预览、参与条件、公开/私有加入链接、报名、规则查看、开奖前复核、满人/定时调度、发奖人员、人品积分、消息延迟删除、活动管理、客户等级、导航/精选推送资格、活动卡状态更新、迁移、回归与 Telegram E2E。

### 1.3 非目标

- 不复制参考 Bot 的随机算法、内部数据库结构或不可观察实现。
- 不提供指定中奖、后台换人、重抽覆盖、修改快照、修改 Winner 或直接改总票数能力。
- 不回写或重算历史已冻结活动、快照、中奖人与票账本。
- 不在未实测前硬编码参考 Bot 的导航/精选门槛、人品消息计分阈值、自然日上限、兑换成本或票数上限。
- 不以静默放行、模拟成功、吞错、默认通过或客户端文案代替真实业务事实。

## 2. 目标信息架构与交互流程

### 2.1 一级命令

- `/start`：发送使用指南图片与命令导航，公开 `/index`、`/new`、`/join`、`/region`、`/myid`，并展示导航频道、精选频道门槛入口。
- `/index`：显示客户等级、累计创建次数、进行中/已开奖/已取消数量，以及可点击的活动分类、发起抽奖、添加到群组、添加到频道。
- `/new`：无草稿时从奖品名称开始；有有效草稿时直接恢复同一草稿的最终预览。
- `/join`：只读列出用户参加过的抽奖；空状态固定为“您未参与任何抽奖”。
- `/region`：选择省级归属地区；首次确认后 5 分钟内可修改，随后锁定 30 天；页面提供“关闭当前页面”。
- `/myid`：只读返回当前 Telegram 用户 ID。

### 2.2 `/new` 首次创建顺序

1. 回复奖品名称，界面提示“建议控制在 10 个字以内”；合同最大长度仍为 120 字。
2. 回复该奖品的正整数份数。
3. 进入参与条件录入：公开群/频道支持 `@username` 或 ID，私有群/频道支持 ID；一次录入一个，可重复添加。
4. 每次添加后展示已添加列表，允许继续添加、删除单项、清空或返回最终预览。
5. 回到最终预览后补齐活动标题、封面、用户限制、说明、开奖方式、发奖人员等字段。
6. 发布前按字段逐项提示缺口；全部通过后才允许发起幂等发布。

### 2.3 最终预览与按钮布局

预览按正式卡片业务文案展示：抽奖标题、封面、用户限制、地区限制、参与条件、奖品内容、抽奖说明、人品加成、开奖方式、发奖人员，并注明“本页面为预览文案，不是正式效果”。

按钮顺序固定为：

- 活动标题 / 上传封面 / 用户限制；
- 参与条件 / 奖品内容 / 抽奖说明；
- 开奖方式 / 发奖人员 / 人品加成；
- 消息提示 / 发布抽奖；
- 清空配置 / 载入上次抽奖；
- 返回首页。

默认值固定为：用户名可为空、地区全国、人品加成关闭、发奖人员为创建者。未设置必填项显示 `【等待设置】`。

### 2.4 草稿与页面状态

草稿为用户级对象，保存 `draft_id`、单调递增 `revision`、有效期和当前页面消息。每次重新渲染生成新的页面版本，旧页面按钮只能得到“页面已过期，请使用最新页面”，不得修改当前草稿。

新建、载入上次、清空、发布成功都会使旧回调失效。载入上次只复制允许复用的配置，不能复用旧 Campaign ID、远端消息 ID、邀请链接、生命周期任务、资格事实或发布幂等键。

## 3. P0 发布阻断需求

### 3.1 R-P0-01 创建回调注册表与旧页面隔离

系统必须使用单一动作注册表同时驱动按钮渲染、授权校验和 handler 路由，不再维护会漂移的独立白名单。启动检查与测试必须证明每个可渲染 action 恰好存在一个授权 handler，反向也不存在永远不可达的创建 handler。

回调 token 至少绑定 `user_id`、私聊 `chat_id`、`action`、`draft_id`、`draft_revision`、`panel_message_id` 和有效期。授权与状态校验完成后才允许消费一次性 token；未知动作、过期页面、版本不匹配和 owner 不匹配都必须显式报错且不改变草稿。

验收：当前 16 个缺失动作全部通过“渲染 → token → 路由 → handler → 新预览”集成测试；满人开奖、定时开奖和人品关闭在 Telegram 测试账号上可点击。

### 3.2 R-P0-02 报名与开奖的全量资格复核

资格集合固定为活动主群、legacy `required_channel_id` 和 V1.7 `required_chat_ids` 的去重并集。报名时与开奖冻结时必须使用同一聚合规则：任一 `INELIGIBLE` 优先于 `UNKNOWN`；没有不合格但至少一个未知则为 `UNKNOWN`；全部合格才为 `ELIGIBLE`。

开奖冻结必须逐群重新观察并保存每个 chat 的观察结果、远端错误类型和观察时间。`INELIGIBLE` 用户不进入候选池；`UNKNOWN` 阻断快照并按既有任务恢复机制重试，不能默认通过或把旧 `INELIGIBLE` 重置为合格。

验收：覆盖离开主群、legacy 频道、任一额外群、后序群不合格但前序群未知、全部合格和远端未知重试；最终 DrawSnapshot 与冻结资格一致。

### 3.3 R-P0-03 新活动默认关闭人品加成

所有新草稿和新建规则在字段缺失时默认 `luck_mode=off`。界面、领域对象、序列化、载入上次与迁移后的新记录必须一致；不允许由 Python 默认值、JSON schema 默认值或数据库默认值重新变成 `standard`。

历史已发布、运行中或已冻结活动保持原规则，不做静默回填或票权重改写。旧草稿的处理使用显式迁移策略并记录来源；不能把历史 `standard` 推断为用户主动选择。legacy `off/standard/active` 只属于旧规则版本，新规则使用独立的 `human_points_enabled` 与兑换规则 revision。

验收：新用户、新草稿、旧 schema 新建路径均显示关闭且只获得基础报名票；现有冻结 `standard` 活动行为不变。

### 3.4 R-P0-04 必加群/频道必须可加入且可定位失败项

每个参与条件都必须冻结可执行加入方式。公开群/频道使用稳定的 `https://t.me/<username>`；私有群/频道必须由 Bot 管理的邀请链接提供加入路径。若 Bot 无权创建或管理私有邀请链接，配置阶段或发布前必须明确拒绝，不能发布一个新用户无法满足的条件。

规则页与资格失败页必须指出具体失败的群/频道，并只显示与该条件对应的加入按钮。私有邀请 token 不写日志、不进入通用审计文本、不暴露给非目标用户。

验收：公开群、公开频道、私有群、私有频道、无权限和链接撤销场景均有自动化与受控 Telegram 群 E2E。

### 3.5 R-P0-05 满人触发原子化与 30 天中午兜底

参与者从非合格转为 `ELIGIBLE` 时，必须在同一数据库事务和 Campaign 行锁内完成合格人数判断、门槛首次命中记录、唯一结算触发任务和审计。触发主体是系统 actor，不依赖创建者届时仍是管理员；重复 Update、并发报名、worker 崩溃与任务重试不能重复触发。

满人模式的兜底时间按活动业务时区计算：发布本地日期加 30 天后的 `12:00`，冻结本地表示、时区和对应 UTC instant。不得使用 `now + 30 days` 保留发布时间的时分秒。

系统必须有可审计的 reconciliation 任务发现“人数已达门槛但触发任务缺失”的活动并补建同一个唯一业务键；补建不是静默成功，需记录根因和恢复事实。

验收：PostgreSQL 并发达到阈值只产生一次触发；在提交前、提交后和建任务后的崩溃点可恢复；创建者失去管理员权限不影响系统触发；时区与 DST 边界计算正确。

### 3.6 R-P0-06 发布编排幂等与可恢复

发布请求使用绑定 `draft_id + revision` 的唯一幂等键。首次创建 Campaign 后必须把 `campaign_id` 和发布阶段持久化回草稿/发布请求；任一步失败后的重试返回同一 Campaign，不得再次创建活动、奖品、任务或发布卡。

创建、冻结、保存上次配置、发送发布卡和清理草稿构成显式发布状态机或 saga。只有 durable association 已保存且发布请求被接受后才能清理当前草稿；Telegram 远端副作用继续通过 Outbox 和 DeliveryAttempt 记录确定性。

验收：在每个事务边界注入失败并重试，数据库只存在一个 Campaign、一组 Prize/Job 和一个远端发布意图；reconciliation 能识别并恢复卡在中间态的请求。

### 3.7 R-P0-07 资格聚合不得短路误判

报名资格观察不能在遇到首个 `UNKNOWN` 时停止并遗漏后续 `INELIGIBLE`。实现可并行或顺序观察，但必须收集全部必加条件后再按 R-P0-02 聚合，并把未执行的观察视为实现错误而不是未知通过。

验收：构造“第一个未知、第二个不合格”和“第一个不合格、第二个未知”时结果均为 `INELIGIBLE`，且保存两项观察事实。

## 4. P1 完整业务能力需求

### 4.1 R-P1-01 参与条件累加编辑

参与条件一次输入一个并追加，不得覆盖已有列表。相同 chat ID 去重；公开用户名解析到同一 ID 时也视为重复。页面展示冻结标题、类型、公开用户名/私有标识和验证状态，支持删除单项、清空全部、继续添加与返回。

参与条件数量上限必须是显式产品配置。现有实现值 10 可作为本项目初始配置，但参考 Bot 的精确上限尚未证明，不能把 10 宣称为对标规则；达到配置上限时明确提示，不能静默丢弃新输入。

### 4.2 R-P1-02 发奖人员解析与历史冻结

发奖人员默认创建者，也可输入 Telegram 用户 ID 或 `@username`。发布前解析并冻结 `issuer_user_id`、`issuer_username_at_publish`、`issuer_display_name_at_publish` 和来源 `creator/custom`。无法解析时保留原输入并拒绝发布，不得降级成“活动创建者”。

正式活动卡、规则页、开奖结果和中奖私聊始终显示冻结发奖人员；用户后续改名不改变历史文案。消息提示开关不能隐藏发奖人员。

### 4.3 R-P1-03 消息提示改为延迟删除

“消息提示”只控制参与完成提示的删除策略，提供同步删除命令开关，以及 10/20/30 秒、1/5/10/30/60 分钟和不删除选项。删除策略在活动发布时冻结，并展示当前选择。

参与完成后先确认业务结果，再按策略创建唯一删除任务。Telegram 删除失败要记录远端错误并按确定性策略处理，不回滚报名、资格或票账本。资格失败、关键错误、活动规则、开奖结果和发奖人员不受此策略抑制。

### 4.4 R-P1-04 独立人品积分与兑换票体系

人品积分与 Campaign 票账本分离。已确认的参考语义是：有效群消息累积人品，并受自然日上限约束。具体有效消息最小长度、每条增加值和自然日上限尚未完成实测，保持 `TBD/unproven`；消息去重、机器人/服务消息排除和隐私指纹沿用现有可靠事件边界。

用户通过明确动作把指定必加群中的人品兑换为指定活动额外抽奖票。不同必加群可配置不同兑换成本；单活动兑换票上限可配置。未完成实测的默认成本与上限保持 `TBD`，实现前由产品配置确认，不得写死猜测值。只有使用 V1.8 人品规则版本且已开启人品的活动可接收兑换；legacy 活动不得混入 `human_redeem` 票源。

新增查询入口：`人品`、`人品排行`、`人品规则`。管理员可增加或减少积分，但必须校验权限、填写原因并保存调整前后值、操作者、目标用户、群、时间和业务键。积分账本只追加；兑换在一个事务内扣减积分并向 TicketLedger 写唯一 `human_redeem` 票源，重复请求不重复扣分或发票。

积分按 `user_id + chat_id` 归属，兑换时显式选择 Campaign，消除同群多个活动时“自动挑一个活动”的歧义。开奖仍只消费冻结的 TicketLedger 权重，不能直接读取或修改积分决定中奖。

### 4.5 R-P1-05 `/index` 活动管理闭环

`/index` 显示客户等级与权威状态计数。进行中、已开奖、已取消分类必须是可点击入口；列表项可进入活动详情。详情根据当前 Campaign 状态和操作者权限只展示允许动作，例如暂停、恢复、提前截止、开奖、取消、领奖登记和查看审计。

未公开 `/menu` 不再作为主要管理入口；若为兼容保留，只能跳转到同一活动详情服务，不能维护第二套权限或状态逻辑。

### 4.6 R-P1-06 规则查看与报名分离

“查看活动规则”和“立即报名”必须使用不同深链 payload、不同 handler 与不同审计动作。规则页为只读，绝不能创建 Participant、发基础票、生成邀请链接或改变资格状态；报名必须由用户明确点击。

规则页展示冻结的用户/地区限制、全部必加群及加入按钮、奖品、开奖方式、发奖人员、人品规则、消息删除策略和当前活动状态。

### 4.7 R-P1-07 客户等级与导航/精选推送能力

`/start` 与 `/index` 提供导航频道、精选频道门槛说明入口。系统需要客户等级、门槛规则版本、资格计算、推送申请、审核/拒绝原因、投放状态和审计记录。门槛计算只能基于权威 Campaign/客户事实。

参考 Bot 的具体等级阈值、导航门槛和精选门槛尚未实测确认，当前值为 `TBD/unproven`。在确认前允许配置规则但禁止以猜测值对用户作资格承诺。

### 4.8 R-P1-08 发布卡状态与入口同步

活动从可报名状态进入截止、结算、已开奖或已取消后，系统通过同一远端消息标识更新发布卡状态并移除/替换报名按钮。旧深链即使被转发，服务端也必须按 Campaign 权威状态拒绝新的报名副作用。

有封面与无封面卡分别使用 caption/text 的幂等编辑路径；远端编辑失败进入 DeliveryAttempt 事实与恢复，不改变数据库权威状态。

### 4.9 R-P1-09 规则展示必须反映冻结配置

创建预览、正式卡、规则页、中奖通知中的人品、开奖方式、发奖人员和参与条件必须来自同一冻结配置投影。自定义抽奖说明不能覆盖或隐藏强制规则；人品关闭时不得继续展示“活跃/邀请自动加票”。

正式活动卡的截止和开奖时间必须在最终 Telegram 渲染边界按活动冻结时区转为 `YYYY年MM月DD日 HH:mm (本地时区)`，不得把 ISO 8601、UTC 偏移或数据库原值直接展示给普通用户；最终边界同时兼容已排队的旧 ISO 载荷。公开开奖结果不得展示完整 `snapshot_hash`、随机输入、请求哈希或内部 ID，只输出业务结果和可理解的冻结依据说明。完整快照哈希继续保存在 `DrawSnapshot` 与内部 Outbox 事实中，不删除、不缩短、不改写，也不回写历史开奖结果。

公开投影必须覆盖 `send_message`、图片 caption、消息/图片编辑、callback 后续提示和 Outbox 最终发送，不允许管理页、个人列表或创建页面绕开该边界。Campaign 状态与报名资格状态必须由穷尽映射转换为中文业务标签；新增枚举若没有公开标签应在测试或运行时显式失败，不得回退到 `.value`、字段名或英文枚举。

所有公开时间都必须同时携带一个权威时区来源：活动相关页面使用冻结 `Campaign.timezone`，非活动用户资料使用机器人业务时区。查询 DTO 必须把所需时区随 datetime 一起返回，不得按 UTC、服务器本地时区或配置默认值猜测活动时区。创建预览、个人参抽/创建列表、地区锁定提示和正式活动卡使用同一格式器与时区标签。

只有显式标记为可公开的业务校验错误可以向用户展示经审查的中文文案。其他 `DomainError`、`ValueError`、Telegram API 错误、callback action/token 原因、UUID、数据库键和模型字段只进入带异常类型与堆栈的结构化日志；用户收到稳定的中文分类提示，失败仍保持失败，不吞异常、不伪造成功。用户主动执行 `/myid` 时可显示本人 Telegram 用户 ID；callback_data、深链 payload 和内部审计标识不得进入消息正文。群/频道缺少可读标题时显示“未命名群组/频道”，不得用原始 chat ID 充当标题。

新生成的报名深链和资格验证 callback 必须使用独立随机、不可由数据库主键推导的 Campaign 公开引用；公开引用与内部 Campaign UUID 分列保存并唯一约束。已发送的 `join_<Campaign UUID>` 只保留服务端只读兼容，新的卡片、按钮和失败回执不得继续生成或展示该协议。持久化 Update 入箱时必须把公开引用或 legacy UUID 解析回同一内部 Campaign ID，再写入权威路由字段，不能因脱敏造成结算排空漏算截止前更新。

Telegram 专属邀请链接名称必须使用独立随机标签，创建意图写入 durable Outbox 后冻结，远端重试复用同一标签，成功后原值写入 InviteLink。标签不得截取 Participant UUID、Campaign UUID、用户 ID 或其他内部键，也不得在每次重试时重新随机。合法但未配置中文名称的 IANA 时区统一显示“活动当地时间”；创建器只展示可照抄的时间示例，管理员成功提示只使用业务语言，不出现 Python 格式串、数据库或投递实现术语。

升级前已经持久化、但尚未开始 Telegram 调用的 legacy 邀请 Outbox，必须在领取锁内一次性替换为中性随机标签，同时重算请求哈希后再交给 Gateway；`PENDING`、`RETRY_SCHEDULED` 和 `gateway_started_at IS NULL` 的过期领取均适用。已经开始远端调用、进入 `UNKNOWN_HOLD` 或已经确认的记录不得只改本地名称，否则会伪造远端事实；既有远端邀请链接名称和已发送历史消息不在本地迁移中追溯改写，需以远端确认的独立 reconcile 事实验收，当前保持 `unproven`。

### 4.10 R-P1-10 多奖品完整编辑

奖品支持连续添加、按顺位展示、删除单项、清空全部和返回。每个奖品名称去除首尾空白后 1–120 字，界面提示建议 10 字以内；份数为正整数。添加顺序冻结为开奖顺位，发布后不能重新排序。

## 5. P2 交互与文案一致性

### 5.1 R-P2-01 用户限制使用内联互斥选择

“用户名必须设置 / 用户名可以为空”使用内联按钮，当前项带勾选。地区默认全国，最多选择 3 个省级地区；选中状态、超限提示和返回路径都在同一设置页完成，不要求用户输入自由文本开关。

### 5.2 R-P2-02 说明、封面与关闭页面

抽奖说明支持设置、清空和返回；空值明确显示 `[ 空 ]`。封面支持上传图片、清除和返回，只保存 Telegram `file_id`。`/region` 页面提供“关闭当前页面”，关闭仅撤销页面交互，不删除已确认地区。

### 5.3 R-P2-03 发布校验按字段反馈

发布校验按创建预览顺序返回具体缺失字段与修复按钮，不只返回聚合字符串。输入错误保留当前草稿与已完成字段；每个错误页面提供返回当前设置或最终预览的路径。

### 5.4 R-P2-04 使用指南与命令菜单

`/start` 使用指南图片、BotFather 命令菜单和页面内命令文案必须同源，至少包含 `/index`、`/new`、`/join`、`/region`、`/myid`。部署后需回读 Bot API 命令配置并在 Telegram 客户端验证，仓库静态文案不能代替该证据。

## 6. 数据与迁移合同

### 6.1 草稿与回调

最低数据事实：`draft_id`、`revision`、`owner_user_id`、`current_panel_message_id`、`expires_at`、`publish_request_id`、`published_campaign_id`。回调 token 保存或可验证相同绑定字段，消费记录与拒绝原因可审计。

### 6.2 参与条件与资格观察

每个冻结参与条件至少保存 `chat_id`、标题、chat 类型、公开用户名、加入方式、私有邀请链接引用、解析时间与规则 revision。资格观察按 `campaign_id + participant_id + qualification_phase + chat_id` 唯一，保存状态、Telegram 错误分类、观察时间和尝试号。

### 6.3 发奖人员

Campaign 冻结发奖人员 ID、发布时用户名、发布时展示名和来源。历史读取不依赖 Telegram 实时资料。

### 6.4 满人触发

保存门槛、首次命中人数、命中时间、系统 actor、唯一业务键、trigger job ID、兜底本地时间、时区和 UTC instant。reconciliation 的发现与修复写独立审计事实。

### 6.5 消息删除

冻结删除模式与延迟秒数。删除任务按 `campaign_id + participant_id + completion_message_id + policy_revision` 唯一；保存远端 message ID、计划时间、执行结果与 Telegram 错误确定性。

### 6.6 人品积分

至少包含追加式人品账本、每日获取计数/水位、兑换规则 revision、兑换事务和管理员调整审计。余额只能由账本聚合或可重建缓存得出；禁止直接修改余额字段。兑换事务与 TicketLedger 通过唯一业务键关联。

### 6.7 发布与推送

发布请求保存幂等键、阶段、Campaign 关联、Outbox 关联、最后错误和恢复时间。客户等级与导航/精选推送保存规则版本、计算输入摘要、申请状态、审核结果、远端投放事实和审计。

### 6.8 迁移规则

- 新草稿与新规则默认人品关闭；历史冻结规则不改写。
- legacy `standard/active` 非终态活动继续按冻结旧规则产生原活跃票/邀请票直至终态；V1.8 新活动不再产生这两类 legacy 自动加成票，开启人品后只通过显式兑换写入 `human_redeem`。
- 不把历史活跃票/邀请票转换成人品，不以人品重算历史票，也不允许向 legacy 活动兑换人品票；旧 TicketLedger、Snapshot 与 Winner 全部保持原事实。
- 载入 legacy 最近配置时复用其他允许字段，但不复制 `standard/active` 为新人品开启状态；新人品默认关闭，需创建者在新页面显式选择并记录来源。
- 人品账本从功能切换点开始追加，不根据旧消息或旧票反向补分；切换点、规则 revision 与启停操作必须可审计。
- legacy `required_channel_id` 继续进入开奖复核，直到受治理的数据迁移完成；不得删除兼容读取后让旧活动少校验一个频道。
- 新增枚举、票源或列宽时数据库约束、SQLAlchemy 模型和 Alembic 必须一致。
- downgrade 遇到无法无损表示的新积分、兑换、资格观察或发布状态数据时明确拒绝，不得删除事实后降级。
- 迁移必须通过空库升级、生产形状升级、downgrade/upgrade、模型漂移和旧活动读取回归。

## 7. 事务、幂等与失败恢复

### 7.1 事务边界

- 报名资格完成：Participant 状态、基础票、资格观察和满人门槛判断在受控事务中提交；Telegram 观察在事务外执行，通过 request hash 与尝试号回写。
- 满人触发：门槛命中、唯一触发事实和 Job 同事务提交。
- 人品兑换：积分扣减账本、兑换记录和额外 TicketLedger 同事务提交。
- 发布：数据库阶段通过显式状态机衔接；Telegram 发送只由 Outbox 执行。
- 开奖冻结：全群资格观察完成且无 UNKNOWN 后，才允许生成唯一 DrawSnapshot。

### 7.2 幂等键

最低唯一业务键包括：创建回调、发布请求、Participant 报名、基础票、每群资格观察、满人触发、兜底 Job、人品消息积分、积分兑换、管理员调整、删除任务、发布卡编辑、DrawSnapshot 和 DrawRun。

### 7.3 失败暴露与恢复

权限不足、Telegram 未知结果、链接创建失败、旧页面、发布中间态和积分不足必须形成明确错误与结构化日志。不得吞掉异常后返回成功。unknown 远端副作用继续进入 hold/reconciliation，不能盲目重发。

公开错误投影与内部诊断必须分离：日志保留异常类、原始原因、堆栈和关联业务键；Telegram 文案仅展示显式可公开校验文案或稳定的业务分类提示。任何原始异常字符串都不得通过统一 catch 路径拼入用户消息。

## 8. 兼容、安全与隐私

- 历史 Campaign、RuleRevision、TicketLedger、DrawSnapshot、DrawRun、Winner 和远端消息事实保持不可变。
- 任何修复不得重抽、补抽、替换中奖人或改变历史权重。
- callback 必须绑定 owner、chat、draft revision 和页面；管理动作继续复核当前 Telegram 管理员权限。
- 私有邀请链接和 token 不写入普通日志、错误回显或通用分析事件；只在授权边界按引用读取。
- UUID、数据库主键、快照/请求哈希、callback action/token 原因、Telegram API 原文和原始枚举不得进入普通用户消息；公开深链/callback 使用独立随机引用，Telegram 邀请链接名称使用冻结随机标签，完整事实只保存在授权日志、审计表和内部 Outbox。
- 人品管理员调整要求当前权限、原因、幂等键和完整审计；不能提供无审计的数据库改分入口。
- 所有用户文本、用户名、chat 标识和日期在边界校验；数据库查询参数化。
- 不新增模拟发布、假远端 message ID、默认合格、默认已加入或健康即成功路径。
