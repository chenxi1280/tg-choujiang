# TG 群抽奖机器人 V1.7 LotteryBestBot 功能对标合同

状态：开发合同
日期：2026-08-08
基线：V1.6 极简交互重构版

> 2026-08-10 审计纠正：本合同中“消息提示”和“人品加成”的语义不完整，且当前实现存在创建回调、开奖前多群复核与默认值等发布阻断。V1.8 修复与验收以 `docs/development/v1.8-lotterybest-repair-prd.md` 为当前权威合同；本文件保留为历史基线。

## 1. 决策

V1.7 对标 `@LotteryBestBot` 已实测确认的信息架构和用户功能，但不复制其开奖随机内核。创建、管理、个人资料与查询入口按参考产品的业务语言重构；开奖继续使用本项目的票数账本、资格复核、不可变快照、多奖品顺位和 `sha256-weighted-v2`。

任何未完成实机观察的参考页面都不能写成已确认事实。实现可依据本合同提供等价能力，验收时仍需在本项目 Bot 上逐项证明。

## 2. 一级命令

### 2.1 `/start`

显示使用指南和主菜单。至少公开 `/index`、`/new`、`/join`、`/region`、`/myid`。

### 2.2 `/index`

显示抽奖管理首页：

- 累计创建次数；
- 进行中、已开奖、已取消数量；
- 发起抽奖；
- 查看三类活动；
- 添加到群组；
- 添加到频道。

活动分类必须由 Campaign 权威状态计算，不能由消息文案猜测。

### 2.3 `/new`

- 没有草稿时直接进入奖品名称；
- 完成奖品名称和份数后，若只有一个可管理群则自动绑定；
- 有未完成草稿时直接恢复最终预览；
- 草稿为用户级、24 小时有效，并记录面板消息 ID；
- 发布成功后保存“上次抽奖配置”，再清理当前草稿。

### 2.4 `/join`

只读列出当前用户参加过的抽奖。每项至少包含标题、状态、报名资格、票数和开奖时间；空状态返回“您未参与任何抽奖”。

### 2.5 `/region`

设置用户归属地区。首次设置后 5 分钟内允许修改；超过 5 分钟后，距上次确认满 30 天才允许再次修改。每次变更保存旧值、新值和时间事实。

### 2.6 `/myid`

只读返回当前 Telegram 用户 ID，不附加敏感资料。

## 3. 创建预览

最终预览按参考产品的成品文案展示：

1. 抽奖标题；
2. 封面设置；
3. 用户名限制；
4. 地区限制；
5. 参与条件；
6. 奖品内容；
7. 抽奖说明；
8. 人品加成；
9. 开奖方式；
10. 发奖人员；
11. 当前发布缺口。

主按钮为三列业务入口：

- 活动标题 / 上传封面 / 用户限制；
- 参与条件 / 奖品内容 / 抽奖说明；
- 开奖方式 / 发奖人员 / 人品加成；
- 消息提示 / 发布抽奖；
- 清空配置 / 载入上次抽奖；
- 返回首页。

## 4. 字段合同

### 4.1 活动标题

必填，去除首尾空白后 1–80 字。

### 4.2 封面

非必填，只接收 Telegram 图片。草稿和正式活动保存 Telegram `file_id`，不得依赖本地临时文件。发布卡片使用照片说明或等价媒体发送，后续取消编辑必须仍能定位远端消息。

### 4.3 用户限制

- `username_required=false`：用户名可为空；
- `username_required=true`：必须设置用户名；
- `allowed_regions=[]`：全国；
- 非空地区最多 3 个，且只能来自固定省级枚举。

报名开始时先校验用户名与用户资料地区，再进行 Telegram 群/频道资格观察。缺失地区资料时明确提示先执行 `/region`。

### 4.4 参与条件

活动必须绑定一个本项目已登记、当前用户具备管理员权限的主群。额外条件逐个输入公开 `@username` 或数字 ID；发布时解析并冻结 chat ID、标题、类型、用户名。Bot 必须是每个额外群或频道的管理员，并有能力调用 `getChatMember`；无法验证时拒绝发布，不静默放行。

### 4.5 奖品内容

支持多奖品；每个奖品按“名称 → 正整数名额”采集。添加顺序即开奖顺位。名称最大 120 字，界面提示建议 10 字以内。

### 4.6 抽奖说明

非必填，最多 500 字。与中奖后的领奖说明是不同字段。

### 4.7 人品加成

这是本项目加权票能力的业务入口：

- 关闭：只使用报名基础票；
- 标准：启用标准活跃票与邀请票；
- 高活跃：启用高活跃预设。

每位合格报名者固定获得 1 张幂等基础票。关闭模式仍记录活跃与邀请事实但不发奖励票，标准和高活跃模式按各自预设发放奖励票。页面必须明确“每张票等概率、总票数越多权重越高”，不得暗示可操纵指定中奖人。

### 4.8 开奖方式

支持两个调度入口，但共享同一开奖算法：

- 定时开奖：输入本地 `YYYY-MM-DD HH:mm`；系统派生截止和结算时间；
- 满人开奖：输入正整数参与人数；达到门槛后进入安全截止、排空、资格复核、快照和开奖流程。发布时同时冻结 30 天兜底开奖时刻。

满人模式不能绕过 Durable Inbox 排空、资格复核或不可变快照。参考产品的“立刻开奖”在本项目中定义为“立刻启动安全结算流程”。

### 4.9 发奖人员

非必填，默认创建者。可输入用户 ID 或用户名；发布时冻结标识和展示文案。

### 4.10 消息提示

显式开关，只控制 Bot 是否附加扩展说明；无论开关如何，关键失败、资格不通过、参与结果和开奖结果都必须明确发送。

## 5. 数据合同

### 5.1 用户资料

新增用户资料权威记录：`user_id`、`region`、`region_selected_at`、`region_editable_until`、`region_locked_until`、`last_draft`、`last_draft_saved_at`。地区变更通过 `UserRegionChange` 保存旧值、新值和时间审计；最近配置超过 24 小时不得载入。

### 5.2 Campaign 冻结数据

正式活动新增 `presentation` JSON，保存封面、说明、发奖人员、消息提示和额外参与条件；所有资格、地区、开奖模式与满人门槛进入 `CampaignRules` 和 RuleRevision，发布后冻结。

### 5.3 报名基础票

每个 ELIGIBLE 报名者通过 `TicketLedger` 的 `registration` 来源获得且只获得 1 张基础票。Update 重放、重复资格完成或并发处理不得重复记票。

### 5.4 满人触发

每次参与者变为 ELIGIBLE 后，在 Campaign 行锁内统计符合条件的人数。首次达到门槛时创建唯一提前结算任务和审计；重复报名、Update 重放和并发完成资格不能重复触发。

## 6. 安全与兼容

- 旧活动缺失新增字段时按显式 schema 默认值解析，不改变历史开奖结果；
- 新字段必须由迁移创建，迁移需支持 upgrade/downgrade 和模型漂移检查；
- 发布动作仍复核 Telegram 管理员与邀请链接权限；
- 图片、用户名、群标识和地区输入在边界校验；
- 不增加模拟发布、假成功或吞错路径。

## 7. 验收矩阵

- 自动化：命令路由、首页统计、参加列表、地区 5 分钟/30 天、草稿恢复、载入上次、封面输入、用户名/地区限制、多参与条件、两种开奖模式、人品加成、发布冻结和旧规则兼容；
- 质量：Ruff、全量测试、代码度量、Alembic upgrade/downgrade/upgrade、模型漂移；
- 发布：`master -> release -> GitHub Actions`，回读 deployed SHA、迁移 head、app/worker 健康与 RestartCount；
- Telegram E2E：逐条命令、全部创建按钮、草稿恢复和输入错误；禁止为了验收发布真实测试抽奖；
- 报名、满人触发、计票、邀请和开奖如无受控测试群，必须标记 `unproven`。
