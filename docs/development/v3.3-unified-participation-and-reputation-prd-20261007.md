每个新活动都要求参与者完成以下四项平台条件，并继续完成该活动原有的参与群、创建者额外准入条件、用户名/地区限制和行为门槛：

| 平台必备条件 | 可验证的完成动作 | 管理范围 |
|---|---|---|
| 启动本抽奖机器人 | 本人在本机器人私聊发送有效 `/start`（含活动深链参数），Inbox保存并完成启动事实的幂等投影；保留后续屏蔽状态 | 平台固定，创建者不可关闭 |

| 关注抽奖导航频道 | 同上 | 同上 |
| 关注精选推荐频道 | 同上 | 同上 |

### 3.1 「关注机器人」的可实现口径

Telegram 的机器人入口是启动私聊交互，本方案将业务用语「关注机器人」实现为「启动本抽奖机器人」。只点击链接、打开聊天页、在群里点击按钮、把机器人加入群，都不算启动完成。页面使用「启动抽奖机器人」，避免让用户寻找不存在的频道订阅动作。[Telegram 机器人交互与深链说明](https://core.telegram.org/bots/features#deep-linking)。

启动记录归属 `bot_id + user_id`，可以用于该机器人下的多个活动，无需每场重复启动。平台只使用本抽奖机器人，不新增另一台需要用户关注的 Bot。

屏蔽与解除屏蔽由私聊 `my_chat_member` 事件以及明确的投递错误更新；Telegram 官方文档说明该事件在私聊用于机器人被屏蔽或解除屏蔽的变更。[Telegram Update 定义](https://core.telegram.org/bots/api#update)。

**能力边界：**没有已核实可用的「机器人关注查询」作为本方案依赖。已收到启动、解除屏蔽或私聊投递成功，只证明相应时点的事实，不能保证此刻或开奖后仍可私聊；删除聊天、静音、阅读消息、打开通知不属于可强制验证条件。规则写为「须启动机器人；系统已确认屏蔽时暂不具备资格」，不承诺持续在线或每条私信一定可达。禁止用群回调清除已知屏蔽事实，禁止为每次核验群发探测私信。

### 3.2 「关注频道」的可实现口径

对三个频道分别调用 `getChatMember(channel_chat_id, user_id)`；**本抽奖机器人必须是三个频道的管理员**，官方仅在此身份下保证对其他用户的成员查询可用。[Telegram getChatMember](https://core.telegram.org/bots/api#getchatmember)。

本期要求的是成员身份，不检查消息阅读、通知开关或付费订阅。公开和私有频道都以稳定 `chat_id` 为核验身份，频道名称和链接仅供展示、跳转。私有频道的入群申请只是待审批，批准后成员核验通过才算关注成功。

## 5. 统一资格、独立加成及历史兼容

### 5.1 资格与次数

```text
平台条件通过 = 本机器人已启动、无已知有效屏蔽事实且关系证据无未解决冲突
             AND 使用说明频道成员核验通过
             AND 抽奖导航频道成员核验通过
             AND 精选推荐频道成员核验通过

成员及其他条件通过 = 平台条件通过 AND 原活动成员及其他条件通过
最终可开奖资格 = 已明确登记 AND 最终成员及其他条件复核通过 AND 行为门槛达标
有效抽奖次数 = 最终可开奖资格 ? 原合同累计抽奖次数 : 0
```

累计次数 = 基础次数（0或1）+累计活跃加成+累计邀请加成；两类奖励可同时存在。未达行为门槛时加成暂存且有效次数为0，门槛达标不再额外发基础票。资格未知时显示“待核验”，不将其当作确定不合格；最终复核仍按§12阻断快照。

- 三个频道必须全部通过，不能任选一个。平台条件没有奖励次数，关注不发加成。
- 查看活动或关注频道不自动登记。本人首次点击「登记参与」可以保存参与意图；缺少平台条件时显示「已登记，平台条件待完成」，不显示报名全部成功。
- 只有首次全部成员及其他条件通过后，才沿用原合同发一次基础次数并启动本场计数；重复启动、登记、检测、退订重订不能重复发放或重置计数起点。
- 平台条件尚未通过时，不提前启动行为计数，不回填首次合格前的发言。已经启动过的统计，后续资格变更沿用 V3.0 来源时点核验与待复核规则。
- 之后退订或确认屏蔽使当前有效次数为 0；保留已登记记录、已取得的行为达标事实和原账本，不扣回已确认邀请奖励。首次已发的基础次数保留，仅当前有效性改变。
- 已登记用户重新订阅/解除屏蔽后，可以在最终复核完成前恢复成员资格；截止后的新增登记、发言、邀请与奖励仍按原截止合同拒绝。本版成员判定以最终复核观察时点为准，不用一次 API 查询伪造截止瞬间的历史成员状态，也不承诺整个活动期间连续订阅。
- 最终快照形成后，继续退订或屏蔽不改写名单、次数、中奖结果。领奖私信无法投递按 Outbox 的明确失败/未知事实处理，不重新开奖或换人。

### 5.2 创建权限和策略冻结

1. 所有本版策略启用后新发布的活动都包含四项平台条件；创建者没有关闭、删除、更换频道的入口。
2. 创建者可继续设置原有额外群/频道准入条件，与平台条件执行 AND。官方频道授权由平台负责，创建者只需满足原参与群和额外目标的管理员要求。
3. 同一 `chat_id` 同时出现在官方条件与额外条件时按一个目标核验和展示，保留所有来源；官方来源不因删除额外条件而消失。频道不能成为活跃发言或邀请计奖目标；平台目标不自动扩展这些奖励范围。
4. 已发布、已结束活动不补加平台条件，不更改冻结规则、截止、开奖时刻及历史结果。上线前草稿继续保留，发布时加载新策略，必须展示变化并重新确认。
5. 「载入上次」只复用原可编辑设置；新的活动采用发布时的平台策略，不能复制历史活动的关闭状态、Bot 启动观察、用户订阅观察或资格。
6. 平台策略按版本冻结到每个活动，包括 `bot_id`、三个频道角色/稳定身份、名称快照及规则说明。不能在报名或开奖时直接读取可变环境变量替换目标；三个角色不可静默合并到一个频道。
7. 配置变更默认只影响后续发布活动。原频道改名但 `chat_id` 不变可更新展示/合法跳转入口；更换频道身份只能生成新策略，不能临时要求旧活动用户补关注新频道。



### 5.3 加成组合与24小时覆盖

| 活跃（人品） | 邀请 | 结果 |
|---|---|---|
| 关闭 | 关闭 | 只有原合同基础次数，行为门槛仍执行 |
| 开启 | 关闭 | 按逐群活跃规则自动加票 |
| 关闭 | 开启 | 按逐群有效邀请自动加票 |
| 开启 | 开启 | 两类各自计数、各自入账、可以同时生效 |

行为门槛仍在发言/邀请中二选一，不受这四种组合限制；两种门槛×四种加成共八种组合保留验证。邀请门槛开启但邀请加成关闭时仍能获取本场本人邀请入口，只推进人数门槛，不发奖励票。

新V3.3活动的邀请门槛与邀请加成共享**入群满24小时后核验**，不出现立即或48小时选择，不用午夜自然日代替24小时。历史已发布0/24/48小时等冻结值继续执行，不能重算原候选/已确认记录；复用到新草稿时明示留存变化并重新确认。

新场活跃（人品）与邀请加成都不设上限：活跃不设每日轮数上限或累计上限，邀请不设累计上限；保留各群每轮消息数/奖励与邀请比例，按有效事实不断累计。午夜只重置当日统计，不作为封顶。历史已发布的有限规则仍按冻结值执行，不改旧账。

### 5.4 私有入口及历史保护

保留当前“公开卡不散布实际私有邀请”的合同，群名进入同场同目标私聊入口，再展示本来允许的加入按钮；不新增创建者公开私有链接开关。官方频道的入口与身份仍由平台管理。管理员不得直接修改成员奖励票或开奖结果；竞品加/扣积分指令不是我们现有权限入口。

活动取消沿用原状态机、票账和审计，不新增人品扣分/退款流程。没有积分扣除就没有积分退款；中奖/未中奖、领奖登记和实际奖品交付仍分别记录。

## 6. 公告、对应目标链接、完整条件与分享

### 6.1 每个目标就是一个完整条件块

平台三个官方频道、所有必须加入的参与群、额外准入群和频道均取同一冻结目标清单；以稳定目标身份去重，保留展示顺序。展示名称、类型、普通加入入口、本群门槛，不能只列群名或默认用主群条件替代所有群。

```text
📮 参与条件（必须全部满足）：
🎫 加入-[A群]                  ← 群名可点击到A
└ 🎟️ 本场单日有效发言满20条     ← 若真实规则为单日20
🎫 关注-[B频道]                ← 直达B，频道没有发言条件
🎫 加入-[C群]
└ 🎟️ 连续3天，每天有效发言满5条 ← 仅真实配置时展示
```

竞品样例“发言数大于20条”的数学边界是21条；现有合同“满/至少20条”的边界是20条。保留我们已冻结的包含边界，不为了复制文案改变资格，也不把两者混写。历史累计门槛必须写“累计”；无门槛的群不生成虚构缩进行。用户名、地区、登记后统计起点、截止另行可见；频道只展示关注要求。

### 6.2 链接与权限状态

“本场×本目标”的私有入口使用服务端解析的短标识，符合Telegram深链payload长度与字符约束；不把多群清单、个人进度或私有原始邀请塞入URL。入口只定位查看/加入，不自动登记、不授予读取他人个人数据的权限。官方频道的入口刷新由平台负责；创建者仅能更新自己有权管理的活动目标，公开私有邀请仍按原合同限制。

Bot 接收普通群文字需要具备消息可见条件；Bot 管理员或关闭隐私模式时能接收普通用户群消息，开启隐私模式时不能假设这些关键词都会送达。[Telegram Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get)。本项目启用群统计前检查并展示权限准备状态，不用“0人品”掩盖未观察到消息。

其他用户的成员核验依赖 Bot 管理员权限保障；创建邀请链接还需要相应邀请权限。API错误保留“未知/待核验”。[getChatMember](https://core.telegram.org/bots/api#getchatmember)、[createChatInviteLink](https://core.telegram.org/bots/api#createchatinvitelink)。

### 6.3 公告顺序与奖品可见性

主卡严格采用：**活动标题 → 参与条件（逐群可点名称+对应门槛）→ 奖品内容（每奖品独立一行，数量加粗）→ 抽奖说明 → 双加成摘要/规则 → 北京时间截止与开奖 → 发奖人及同场参与链接**。奖品必须在参与条件下面、说明上面；不能放到配置术语、长计数说明或规则链接后才看到。不能把“满3条”照抄成“大于3条”，不改包含边界。

长卡仍按这一顺序生成清单，条件+奖品优先保留在正式主卡。只有可见容量不够时，将较长说明/完整计数规则移到确认的规则续页；不能因为封面caption超长就让主卡丢掉全部条件和奖品。若条件+奖品本身仍超过caption容量，保持封面并发送有完整条件/奖品的有序文字页与回查入口，主卡仍保留独立奖品区及容量允许的完整奖品行，并明确剩余项数、提供全部奖品回查；所有奖品在完整规则页逐项保存，不裁切单个名称或冒充摘要即全清单。分享卡使用相同模板/页清单；每个必要页独立确认，未知不重发。

### 6.4 长文与转发

- 首先保留完整条件块，再考虑奖品和长说明分页；不能一超长就删除全部条件，只留“查看规则”。
- 图文说明装不下完整条件时，采用封面消息 + 紧邻的条件续页 + 主操作消息的原生消息组，页码、活动名和同活动链接在各页可见；条件块不可拆开，单块也超限则发布前提示调整。
- 发布预览同时展示实际消息组结构；“分享活动卡片”向本人发送同样完整卡包，并提示多条需一起转发。每条都保留同活动规则/参与入口，单独转发某页仍能回查全部条件。
- 能放下一条时仍采用单条卡片，不增加中间步骤；长文消息组须逐条确认，全部必要消息确认后才标完整发布。消息组非原子远端操作，部分成功、失败及 UNKNOWN 分开显示与对账。
- 正文群名、缩进门槛、各页链接、主按钮和个人条件页都来自同活动同 revision 投影。群名称转义、同名群辨识、HTML容量检查继续保留。

## 7. 活跃加成（人品加成）规则与反馈

活跃加成是本场逐群有效发言自动加票，采用现有GroupActivityRule/DailyProgress/TicketLedger，不建立跨活动可消费人品余额。

- 各群独立设置每轮消息数N、奖励R；新场每天每满N条自动+R次，不设每日轮数/累计上限，也不提供“每天只奖励一次”或有限上限选项。历史有限活动按原规则读取，不能用最新设计覆盖已发布事实。
- 按北京时间自然日统计，00:00重置今日进度；已入账活跃奖励、已完成门槛保留。活跃自然日与邀请滚动24小时是不同时间口径。
- V3.1短文字、图片、表情、贴纸/GIF按既有消息口径计数；命令、机器人、服务、转发、空白不计，既有重复窗口继续使用。不恢复每条超过3字，不给“人品”命令计聊天数。
- 每场明确登记且首次通过成员/平台等条件后启动统计；登记前不补采，同一消息若在多场分别已登记且满足规则可分别投影，不合并成永久总积分。各群不能互补条数。
- 只有达到本群奖励轮次才自动入账，无需领取/兑换；同群同日目标奖励变化通过唯一业务键结算，重放/并发不重复。
- 行为门槛未完成可照常按已有合同取得并暂存奖励；门槛后来完成只改变有效性。成员资格来源时点失效/未知按V3.0保留待复核事件或明确拒绝，不猜测补计。
- 本群今日条数、下一轮差值、当日奖励及不设上限说明、本群及本场累计活跃奖励、门槛与有效次数分别可见。今日0不代表累计奖励清零，缺可靠查询结果显示待核查，不能伪造0。
- 新场不会以达到奖励上限停止计奖；历史有限活动已达上限不再提示“还差”。本场门槛已完成不每日重新要求达标。连续天数中断只重算未完成门槛进度，不扣历史奖励。
- 暂停/未开始/截止/结束按原窗口停止相应新计数及奖励，保留历史明细；截止前来源事件的合法排空仍按原合同处理。

## 9. 邀请加成：24小时核验、一次归因与窗口

### 9.1 计奖条件与完整时间口径

真实新成员通过本期本人对应群邀请入口入群 → 保存待核验记录 → **连续留在目标群满24小时** → 主动核验真人及对应群成员等原有效邀请条件 → 确认为有效 → 按本群冻结比例自动增加邀请奖励/推进邀请门槛。

- 满24小时是最早核验时间，不承诺恰好到点即送达；网络、429、Worker延迟须显示待核验，不能把延迟当用户无效或提前发票。
- 邀请计奖时钟从Telegram真实入群事件开始；私有群申请从批准并真实入群后开始，不从点击/申请/接收时间算。展示入群时间、预计可核验时刻、目前状态和失败原因。
- 活跃采用北京时间自然日，邀请用入群时刻+24小时；两者不能共用“午夜重置”。时间存UTC、展示Asia/Shanghai，已保存开奖时刻不变。
- 最晚计奖入群时间 = 本场有效截止 - 24小时；等于边界时可成为候选，晚于边界仅可正常入群、不计本期奖励。有效截止有提前关闭时按原较早时间取值，不能继续显示旧截止。
- 截止前产生且due_at不晚于截止的合法候选可在结算中迟到核验；未知保持待恢复，不缩小候选池、不以任务晚执行拒奖。取消/已开奖终态不继续写奖励或改快照。

### 9.2 单一用户同群只计一次

去重身份为**稳定Group × invitee Telegram user_id**，不是昵称、用户名、单条链接或单活动局部编号；单场邀请记录另绑定活动、邀请人和目标群。群级首次来源唯一，只有Telegram真实加入事件携带的那条链接拥有归因。

- 同一用户反复加入同一群、换邀请人/链接、换同群活动都不能再次成为新成员；已是或曾是本群成员明确标不计入，不能靠新链接重置历史。
- 自邀、机器人、来源不匹配、已有成员、仅打开链接、未知入群事实不计。不能用最后点击猜归因，也不能自动把候选绑到最新活动。
- 未确认前退群不算有效；若原规则允许恢复，重新加入只恢复同一原候选/首次归因，重新从实际本次入群时刻连续等24小时，并再次验证最晚入群窗口。不能把两段留存相加或给新邀请人另建奖励。
- 已确认后退群/重进不重复奖励，已获邀请人数及奖励不扣回；链接过期/撤销同样不反扣。邀请人自身资格变化影响当前有效次数，但不删除已确认奖励。
- 同一人在A/B两个不同群分别为真实首次新成员时可各计一次；群升级用稳定Group映射，不因chat_id变化重新计奖。并行活动争同一入群更新由数据库唯一约束决定同一首次来源。
- 受邀人满足本群新成员/24小时规则即可贡献邀请事实，不强迫其先报名本场、启动Bot或关注三个官方频道；其本人要参与抽奖时才需平台四项及本场门槛。不能为邀请有效性偷偷增加另一套参与要求。

### 9.3 操作入口与本人记录

本人明确登记、满足取得入口的成员/平台前置条件后即可获取邀请入口；**不用先完成邀请人数门槛**。只有邀请门槛无邀请加成时仍提供逐群入口，但明确“用于门槛，不增加奖励次数”。

页面展示同场同群确认人数、待24小时/待API核验人数、未计入原因、每X人奖励规则、累计邀请奖励、下一档差值和最晚入群时间。取得邀请入口及记录不依赖开启活跃加成；活跃页不依赖邀请链接。

只有一个群直接详情，多群先选择；确认取得链接后提供复制/转发/本群记录，确认消息尚未完成不假称可用。链接只发本人私聊，群卡回调先回应后私聊，私聊失败不给群里泄露完整个人链接；普通活动分享不能算本人邀请。

截止/开奖后个人旧链接仍按V2.3可入群且保留原归因，不改绑下一场；正文明确本期不再计奖，关闭新增取链接/奖励引导，历史查询可用。明确撤销显示不可用原因，UNKNOWN先核实不盲目生成替代链接。

## 10. 群内查询、完整提醒与操作反馈

### 10.1 查询入口的语义保护

“人品”查询是本项目活跃加成查询，不是返回永久积分余额。R5已补便捷群入口：有唯一可定位活动时显示该场该群活跃进度/已获奖励/下一步；多场必须先选活动，不自动选最新。完整跨群明细仅本人私聊，未登记给同场参与入口、不自动登记。明确活动的群卡/旧深链继续用原ref。

“人品规则”展示本项目有效消息、每日模式、活跃/邀请独立设置、邀请24小时一次归因、门槛暂存和本场冻结参数；不能链接竞品积分规则来代表本项目。“人品排行”已由用户确认按**本场活跃加成已入账次数**排序，跨本场所选活跃群汇总，不含基础票或邀请奖励。同分并列名次，展示顺序按Telegram用户ID稳定排序；未完成门槛的已入账暂存奖励仍参与排名，页面明确排名不代表当前开奖资格。仅显示已登记且本场活跃奖励大于0者，空榜有活动入口。每页10人，按钮保留活动ref、原群和查询者身份，其他人点击旧查询按钮须重新发起自己的查询。多场先选场，不默认最新。

竞品管理员“加人品/扣人品”不接入我们的奖励账本或指定中奖权限；需新增人工调整时另行确认对象、权限与审计合同。群指令精准路由，命令本身不计活跃或门槛聊天；私聊/群聊前置失败仍给可执行的入口，不能无响应。

### 10.3 投递、删除、开关与恢复

业务状态/奖励和通知意图同事务；目标奖励已提交但通知入队缺失暴露断点，不能靠即时私聊掩盖。重复Update/Job/检测不重发奖励或完成通知；删除任务只处理该临时message_id，不删群卡、达标或结果通知。

Outbox待投递/已确认/明确失败/UNKNOWN分别可查；临时发送未知没有确认计时，不提前排删除；删除失败保留原错误和可恢复任务，不说已消失。远端可能已写操作先对账，明确未写才按原重试合同恢复。

扩展提示开关只控制其原可选提示范围，不能关闭必要的本群/全场达标、奖励、截止、群结果和中奖私信；平台阻断反馈不可被静默隐藏。Bot发送显式开启通知，用户客户端声音/弹窗/静音独立验收，不承诺绕过设置。

## 11. 公告与个人加成文案

公告加成区必须明确两种模块，可用项目叫法“活跃加成（人品加成）”“邀请加成”；后者不埋在人品规则里，也不把两者改成积分兑换。

```text
🔋 抽奖加成：
└ 活跃加成（人品加成）：A群每天每满20条 +1次，不设上限
└ 邀请加成：A群每1名有效新成员 +1次，入群满24小时后核验
└ 邀请重复入群只计一次；本场累计不限

```

上例数字仅为冻结配置示例，不给所有群硬编码20/+1；关闭一项只写该项未开启。原项目“人品加成”可保留且要解释是活跃奖励，不判为虚假余额消费；最多9或闪电次数不能暗示统一封顶。平台四项、各目标加入入口与本群门槛仍在参与条件区完整显示。

个人页分开显示基础、累计活跃、累计邀请、当前有效总次数、暂存原因；邀请分确认/待24小时/待API核验/不计入，活跃分今日/累计。门槛与加成不能共用一个误导的完成标记。过去完成时和当前状态分开，历史票与快照不改写，不给无依据的中奖概率百分比。

## 12. 资格核验、失败与开奖证据

### 12.1 状态与失败分类

| 事实/失败 | 目标状态与反馈 | 对资格/开奖的影响 |
|---|---|---|
| 频道返回 `member / administrator / creator` | 该频道通过，保存观察时间 | 仍需其他目标全部通过 |
| `left / kicked`，或明确本人不是成员 | 明确未关注，给真实加入入口 | 本人不合格，不作为平台故障 |
| 群目标返回 `restricted` | 只按 `is_member` 判断成员身份；该类型适用于超级群 | 不把禁言误判为离群；三个频道仍按实际频道类型判断 |
| 申请加入私有频道，尚未批准 | 待审批，不是已关注 | 本人尚未通过 |
| 本机器人从未收到成功处理的启动 | 未启动，给同场私聊入口 | 不发基础次数、不启动统计 |
| 已确认本人屏蔽机器人 | 已知屏蔽，给解除屏蔽/启动指引 | 本人当前不合格，历史账本保留 |
| 明确解除屏蔽且已有启动事实 | 可重新核验；解除屏蔽本身不自动登记 | 不重复发基础次数 |
| 网络错误、超时、429、未知响应 | 核验待恢复，记录错误；429尊重 `retry_after` | 不默认通过、不算未关注、不清空历史观察 |
| Bot 非管理员、被移除、频道不可访问 | 平台目标故障，关联受影响活动 | 暂停新发布与资格放行，平台恢复后再核验 |
| 私聊消息投递失败 | 按明确原因更新 Bot 关系/Outbox；通用403不统一等同本人屏蔽 | 投递失败与订阅、开奖结果分开 |

逐目标保存状态，即使某项已明确不合格，也不能丢掉另外一项未知的原因。聚合页同时显示缺项和系统故障；修复某项不自动将整份资格设为通过。未知响应保留分类和原错误，禁止吞异常或只输出笼统成功。

### 12.2 三层核验

1. **发布前**：验证完整策略、当前 `bot_id`、三个不同频道 `chat_id` 与类型、合法加入入口、本机器人当前管理员身份。失败保留草稿；创建者不受官方频道管理员要求限制。
2. **登记与重新检测**：基于活动冻结目标核验本人；复用已有资格检查、逐目标观察、业务幂等和当前检查的合并逻辑。页面缓存可以展示最近事实，不能单独作为本次通过依据。
3. **开奖前**：冻结报名/行为统计范围后，对已有参与者再次检查三个频道和 Bot 关系事实，合并原成员/其他条件与行为门槛，再形成不可变快照。指定中奖也只能从同一复核结果取得资格。

**本版硬约束：**三个平台频道不能沿用现有「目标访问失败、重试耗尽后降级继续」路径。未知资格不能默认通过，也不能被静默剔除后宣布正常开奖。对仍可能合格但平台条件未能查明的参与者，活动保持「已截止，复核待恢复」，记录阻断、下次重试和原因；只有全部潜在候选已明确通过或明确不合格，才可冻结最终名单。已由其他确定条件排除者可以记录排除原因，不为其无限等待无关查询。

重试有退避和告警，耗尽自动重试后仍保留可恢复阻断，不循环刷 Telegram；运维恢复后只续接同活动、同策略、未完成目标，不重启报名、重发奖励或更换目标。暂停复核不修改已保存的计划开奖时间；页面分别显示原计划与实际执行时间。

### 12.3 事件延迟与证据边界

- 订阅/退订 `chat_member` 作为加速失效与刷新信号；机器人必须是频道管理员，且 `allowed_updates` 显式包含 `chat_member`。仍以主动成员查询完成登记与最终复核，不依赖事件必达。[Telegram Update / getUpdates](https://core.telegram.org/bots/api#update)。
- 启动、屏蔽、解除屏蔽以来源事件时间、Update 身份及稳定顺序归并；重复事件不重复写奖，迟到旧事件不能覆盖较新事实。只有真实私聊启动/交互或明确解除屏蔽证据可更新相应状态。
- 最终复核要记录批次与各目标观察时间，按本稿§12.4的有限事件水位处理已入Inbox的相关更新；若新增退订/屏蔽事实否定复核结果，重新核验受影响候选，不能继续使用已失效的通过结果。
- Telegram 远端变化、Update 接收、数据库提交和快照生成无法做到跨系统原子一致。本版保证使用已获得且未被更新事实否定的证据，不承诺逐毫秒持续订阅，也不从「没有屏蔽事件」推断私信一定可达。
- 已知更新丢失或 Bot 关系证据冲突时标为待核查，通过已有私聊互动或明确关系事件恢复；禁止伪造无屏蔽结论。中奖后才发现私信不达不反改结果。

### 12.4 有限复核水位、竞态与恢复

1. 每轮最终复核固定本场候选集合、冻结策略摘要和已持久化的相关Inbox水位；等待该水位内影响候选的成员/关系事件投影完成，失败事件形成可恢复阻断。不会等待整个Bot收件箱永久清空，也不因其他活动聊天不断到来无限延后。
2. 保存逐目标响应时间、关系/成员证据版本和检查批次。事务内确认水位及证据版本未被否定，再提交快照；快照与取消使用同一活动状态锁。若有新的相关事实改变版本，退出本次提交，刷新受影响候选和新的有限水位，不重复全场已完成且仍有效的工作。
3. 核验结果的最大可使用时长须作为平台策略的明确参数，在实施设计中给出默认值、边界测试及容量依据；不能无限使用数小时前的通过结果，也不能每个Worker自行设定。配置缺失时策略不可启用，超时仅补查受影响目标；容量不足保持“复核待恢复”并告警，不能临时延长期限来放行。
4. Telegram消息时间可能同秒，Update ID在长时间无更新后不保证永久单调。新关系事实按来源时间、Bot、接收会话及明确先后证据归并；冲突不强行取数值最大的Update作为新事实。同秒无法排序标待核查，用新的可靠私聊交互/关系事件恢复。[Telegram Update](https://core.telegram.org/bots/api#update)。
5. 事件投影事务和快照提交必须协调证据版本；提交前已在Inbox内但尚未投影的否定事件不能漏过。快照提交后才到达的远端旧事实可记录迟到审计，不能回写既有快照或换人；这一观察时点边界应在规则与验收中明确。
6. 发生已知更新丢失时，三个频道可以主动重新查询；Bot屏蔽没有等价实时查询，保留待核查，并给本人重新启动的恢复路径。不能为测试可达性给所有参与者发送探测私信，不能以“没有事件”解除已有屏蔽。

### 12.5 邀请候选与最终结算

本场截止前已形成、due_at不晚于截止的24小时候选须接续完成，未知/限流/任务延迟不能直接剔除；明确不满足留存或成员条件才记无效原因。邀请确认、人数门槛/奖励、合并通知与结算快照保持同场来源一致。新平台条件校验的是抽奖参与者本人，不给受邀人额外强制报名/关注要求；指定中奖也不能绕过统一复核。

## 13. 统一数据与可靠性合同

实现依托现有资格链路，不增加另一套抽奖名单或奖励账本。以下字段为设计语义，具体命名随迁移评审确认。

| 数据/模块 | 必须保留的信息及用途 |
|---|---|
| 平台策略配置 | `policy_version`、启用范围、`bot_id`；`guide/navigation/featured` 三个角色各自的稳定 `chat_id`、展示名、加入入口；完整性和身份检查结果 |
| 活动冻结策略 | 发布事务保存策略版本/摘要/hash与平台目标；资格、公开展示、复核均读取此版本，不动态追加当前默认条件 |
| 统一资格目标 | 保留现有目标种类/稳定身份，另存 `platform / creator / participation` 来源集合；平台锁定与权限来源独立，同身份合并后保留所有来源，不能用来源字段覆盖目标类型 |
| Bot 用户关系 | `bot_id + user_id` 唯一；首次启动时间与来源Update、最新关系状态/来源时间/Update、已知屏蔽或冲突；派生字段不得覆盖原事实 |
| 资格检查与观察 | 复用 `QualificationCheck`、`QualificationTargetObservation` 保存平台频道、状态、观察时间、attempt、错误、目标摘要；Bot 关系检查关联证据记录，不把 `bot_id` 伪作频道 `chat_id` 调用成员接口 |
| 运行阻断 | 复用既有阻断与恢复机制，按平台目标影响的活动归属；新策略保留强制阻断，不能由历史降级代码自动清除 |
| 最终快照 | 关联本场冻结策略、最终复核批次及证据摘要；保留排除原因、名单/次数与规则hash，历史查询可解释为何不入名单 |

关键接入点：配置/发布冻结 → 目标汇总 → 私聊启动与关系更新 → 登记/个人条件页 → 频道变更映射 → 最终资格复核 → 快照准入 → 原开奖与通知。既有 Outbox 只承担需要投递的规则、状态和结果消息，资格查询与本地写入不是投递成功事实。

数据库迁移采用可兼容的新增字段/表，缺少本版冻结策略的历史活动明确走旧合同，不能以空策略代表新活动条件已通过。已发布活动有新策略时，旧 Worker/代码若不能理解该策略必须拒绝执行该活动，不可当作旧活动放行。

上述要求不能只靠旧代码自动识别未知JSON字段实现：启用前部署具备能力校验的过渡版本，任务领取与发布写入校验所需规则能力，隔离/停止不具备能力的旧执行器。回滚最低版本必须保留该校验与新数据读取；若回滚到更早版本，先停适用发布和执行，不能让无能力检查的旧Worker接管新活动。

不能因为文档版本为V3.3，就直接替换现有活动 `contract_version`：当前多群与开奖承诺分支有自己的版本集合，新平台策略须独立标识或同步扩展全部相关读取分支，保持多群、邀请和开奖承诺语义。现有轮询通过 `ALLOWED_UPDATES` 枚举接收更新，实施时确认所用SDK包含两个成员事件并保持接收，不把已有事件订阅误列为全新能力。

既有用户的启动状态只能从可验证的本机器人私聊 `/start` Inbox证据回填；没有证据时请本人启动一次，不能由 `UserProfile`、群成员身份或旧报名推断。Bot关系事件可以保存全局事实，但更新既有报名资格只针对使用本版策略的非终态活动，避免改变旧合同或历史结果。每个频道的观察时间取该次响应对应的实际观察时间，不用整批开始时间冒充全部目标同时核验。

### 13.1 保持原有加成与通知事实

| 数据 | 保持的语义 | 本轮必要补充 |
|---|---|---|
| CampaignRules | activity/invite两类独立配置、逐群参数，历史JSON兼容 | 新V3.3固定24小时的明确规则标识/校验，不用人品命名改enum |
| DailyProgress/ActivityEvent | 本场/用户/群/北京时间日计数、奖励目标 | 活跃别名和今日/累计展示；不建立永久积分余额 |
| GroupMembershipFact | 稳定Group×用户唯一首次成员/来源事实 | 页面解释已是/曾是成员、同群跨活动不重复 |
| ReferralRoute/InviteLink/Invitation | 同活动/邀请人/群、真实join来源、due_at/核验状态 | 展示24小时预计核验、确认/待处理/不计入原因；重入只恢复原候选 |
| TicketLedger | 基础/活跃/邀请独立来源、追加式唯一业务键 | 暂存/有效投影，不能新增人品扣分消费或改已确认奖励 |
| 业务通知与Outbox/Attempt | 同事务意图、同来源合并、远端确认/失败/UNKNOWN分开 | 完整矩阵N01–N16的缺口可查，不把送达当奖励事实 |
| 删除Job | 真实message_id与发送confirmed时间+15秒 | 临时删除幂等、失败可恢复，不删必要通知 |
| DrawSnapshot/DrawRun | 冻结最终资格/权重与真实中奖 | 新平台复核结果对应原两类奖励，不改变开奖内核或旧快照 |

无需为“活跃＝人品”新增积分账户、消费票源、退款或人工改分表。实现应以现有加成服务和通知契约补缺，新增平台策略/关系证据不得变成第二套报名或票账。

## 14. 配置、容量、上线与回滚

### 14.1 三个频道的准备

- 运营确认使用说明、抽奖导航、精选推荐三个不同频道的正式身份，分别把本机器人设为管理员；成员查询不额外要求机器人发布频道内容。创建私有邀请链接或审批入群时才申请相应额外权限。
- 现有 `GUIDE_CHANNEL_URL / NAVIGATION_CHANNEL_URL / FEATURED_CHANNEL_URL` 保留导航用途；新增独立强制策略身份配置。现有URL可能指向消息，不能把消息链接当成已验证的频道加入入口。
- 沿用 README 的测试入口边界：当前三个入口仍用于测试，正式 `chat_id`、加入入口、权限及启用时刻需独立确认。本方案不替换现有链接，也不默认把测试频道升级为正式强制关注目标。
- 公共链接须解析并核对同一 `chat_id`；私有加入入口沿用密文、撤销与审计合同。邀请密钥、Bot Token、私有邀请链接明文不进入代码、PRD或检查输出。
- 缺配置、频道重复、类型不是频道、Bot 身份不匹配或管理员预检失败时，新策略不可启用，不能把少于三个频道当作完整配置。

### 14.2 限速、恢复和通知

复用现有限速配置与 Worker 租约；成员查询预算由所有调用者共同约束，不因多 Worker 各自建限速器而扩大总请求速率。并发检测合并，重试只补未完成目标，429按远端要求退避。

新增最终查询量约为 `候选人数 × 3`，另加原目标和预检请求。例如1,000人新增约3,000次；按当前默认20次/秒的配置，理想串行耗时约150秒，实际受共享调用、重试和网络延迟影响。这个配置值不是 Telegram 官方额度或开奖耗时承诺。最终复核需要持久化逐人/逐目标进度，Worker重启接续，不能要求全活动在一次进程里做完。

平台记录目标故障、受影响活动、待复核人数、最近成功核验、重试耗尽及恢复结果。成员本人可查看真实阻断；同一活动/同一阻断阶段的通知走 Outbox 幂等合并，避免恢复循环反复发消息。关闭扩展提示不关闭开奖结果通知；无盲目重投未知消息。

### 14.3 灰度与回滚边界

1. 先实现并在专用测试 Bot + 三个测试频道验证，通过后准备正式身份和权限。
2. 部署兼容新数据结构、可识别策略及新24小时合同但尚未启用的版本；核对 app/worker 版本与迁移，再启用完整新策略，仅对后续发布活动生效。
3. 新发布活动必须看到完整规则再确认；保留一场旧活动验证冻结合同未改变。生产实测活动/报名/开奖按另外的执行授权进行，本 PRD 不触发这些操作。
4. 回滚时先暂停所有适用本版的新活动发布，不回退为无平台条件的新活动。已采用新策略的活动不能删条件或回退到不认识策略的 Worker；使用兼容版本恢复或保持阻断，必要的取消走原授权和审计流程。

## 15. 完整用户路径与页面状态

### 15.1 群卡、转发卡与活动落地页

群公告正文、转发卡、完整规则、活动详情使用同一冻结规则投影，平台条件排在行为门槛之前，正文明确写出：

```text
📌 参与必备条件
1. 启动本抽奖机器人；系统已确认屏蔽时暂不具备资格
2. 关注使用说明频道
3. 关注抽奖导航频道
4. 关注精选推荐频道
5. 加入活动参与群，并满足本活动其他条件

报名时核验成员条件，开奖前再次复核。
发言/邀请要求与额外抽奖次数见下方本场规则。
```

各频道名称可点击；正文参与链接与参与按钮仍是同一个 `https://t.me/<bot_username>?start=join_<campaign_ref>`，沿用当前合法 payload 格式，保留原活动和邀请归因上下文。链接用于回到同场活动，不通过点击判断条件完成。长条件按本稿§6的完整消息组发送；全部必要页及主操作消息确认后才标完整发布，不能用仅有规则跳转的摘要代替可见条件。

### 15.2 未启动与首次登记

```text
群卡/转发卡/活动链接
  → 本机器人私聊收到 /start join_<活动>
  → 显示完整规则和「登记参与」
  → 本人确认登记，保存参与意图
  → 核验平台四项 + 原成员及其他条件
  → 缺项：逐项展示，给关注入口和「重新检测」
  → 全部通过：发一次基础次数，启动计数，继续原行为门槛
```

已经启动过的用户直接进入活动页，不再要求重复启动。群中旧登记按钮不能跳过平台核验；未启动/已知屏蔽时给本人提示和本场私聊深链，个人条件明细只在本人私聊展示。

私聊收到有效 `/start` 并记录启动事实，不等于已登记。发送 `/start` 后页面投递失败时，启动事实与反馈投递分开，恢复不能重复登记或发次数。启动投影不依赖活动页投递、频道核验或草稿挂起成功；该事实完成后，即使后续处理重试也不会要求用户反复启动。

### 15.3 本人条件页

```text
参与条件 · 活动A

平台必备条件（4项全部必需）
✅ 抽奖机器人：已启动；未记录到有效屏蔽事件
✅ 使用说明频道：核验通过 · 10-07 12:01:02
❌ 抽奖导航频道：尚未关注
⏳ 精选推荐频道：暂时无法核验

当前：已登记，平台条件尚未全部通过
下一步：关注抽奖导航频道，然后重新检测。
精选推荐频道的核验故障由平台处理，无需反复退订重订。

[关注使用说明频道] [关注抽奖导航频道]
[关注精选推荐频道]
[重新检测]
[返回活动]
```

- 三个频道的入口一直可见；核验状态和观察时间写在正文，不能只靠按钮颜色表达。
- 未登记时主操作为「登记参与」；已登记缺项时为「重新检测」。检测只推进原登记的核验，不创建新的参与意图。
- 跳转频道不离开本场上下文。重新检测先回应 callback，显示处理中，再更新同面板；连续点击复用同一进行中的检查，不并发重复调用或发奖励。
- 本人频道退订事件可更新已有报名的状态；频道关注/申请事件不能为未登记者创建 Participant。
- 全平台条件通过但其他条件不合格时仍列出原缺项；平台通过但行为门槛未达标时显示「成员条件通过，抽奖门槛待完成」，不能写「已获得最终开奖资格」。
- 已截止页面保留刷新和查询；仅对已有参与者推进尚未完成的最终复核，不开放新登记。已开奖/已取消页展示历史冻结结论，当前订阅情况不覆盖历史结果。
- 所有子页都有返回本场活动和来源列表的路径，保留分类、页码及活动身份，不跳到最新活动。

### 15.4 创建者页面

原「参与条件」父页增加「平台必备条件」只读区：启动本机器人、关注三个官方频道，标明「所有新活动必需，由平台配置」。原额外准入选择器只管理创建者的条件。

不在创建主面板新增四个编辑控件，保持 V3.2 层级；最终预览、发布确认和载入旧草稿后的变化提示都完整展示四项。策略无效时显示「平台频道配置待修复，暂不能发布」，可以继续编辑、保留草稿和返回，不能伪造可发布状态。



### 15.5 参与、双加成、提醒与历史路径

| 路径 | 可见结果与下一步 | 无副作用/恢复 |
|---|---|---|
| 群卡→对应群名→加入 | 对应目标、门槛与申请/加入状态 | 不自动登记/记个人邀请 |
| 群卡→同场启动→登记→核验 | 平台四项+其他条件逐项反馈，缺项有真实入口 | 启动、报名、基础票分别幂等 |
| 未报名发言 | 原群临时提示本条未计进度+同场参与链接 | 五分钟冷却，确认后15秒删除，不补采 |
| 已登记→活跃进度→本群发言 | 今日/下一轮/累计及门槛状态 | V3.1口径、达到奖励自动入账，暂存不扣 |
| 已登记→邀请群→个人链接→复制/转发 | 同场同群归因、满24小时说明、最晚入群时间 | 不要求先满人数门槛，不公开个人链接 |
| 受邀人真实新入群→满24→核验 | 候选→待核验→确认/无效/未知，自动算对应门槛/奖励 | 单群同人一次，受邀人不自动报名 |
| 本群/全场门槛与奖励同源完成 | 一条持久合并提醒，列最终次数及暂存/生效 | 不三连、不同群/日期不乱合并 |
| 已报名但资格失败/未知→加成明细 | 历史奖励可读，原因可见 | 新邀请请求受原资格限制，不错报未报名 |
| 截止/邀请窗口结束→旧邀请页 | 本期不再计奖、仍可按原链接入群、原记录可查 | 不改绑新场，不延长截止、不扣已确认奖励 |
| 页面/通知发送失败→刷新/重试 | 显示真实业务及发送状态 | UNKNOWN先核实，页面重试不重复发票 |
| 开奖→群结果/中奖私信→历史结果 | 同场快照、真实奖品与领奖入口 | 两条独立回执，领奖登记不等于交付 |
