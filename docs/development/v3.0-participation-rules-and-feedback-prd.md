## 1. 问题、目标与范围

| 主题 | 对应原始反馈 | 本次目标 |
|---|---|---|
| R1 达标反馈 | 指定发言条数完成后，多群均未收到成功提示 | 门槛完成、每日任务完成、加成入账、最终资格分别反馈，逐群可追溯 |
| R2 条件展示与前置 | 条件只看到按钮；抽奖链接里看不到具体要求 | 群卡、转发内容、活动链接落地页、规则页统一使用文字和可点击入口，报名之前可读完整条件 |
| R3 门槛与加成独立、多群差异 | 发言与邀请混淆；部分群不希望开启发言 | 门槛严格二选一；两种加成各自开关、逐群配置；新活动邀请加成不限累计上限 |
| R4 自定义时间与快速复用 | 保留自定义时间，快速创建、复用活动 | 保留北京时间输入与快捷时间、载入上次；复用配置不复用旧活动的计数、归因或开奖时刻 |

完成目标是同一活动、同一参与者在多个群中能清楚看到“要做什么、做到哪里、能否参加、增加了几次”。显示已达标、票数已入账和 Telegram 消息已送达是三项独立事实。

本次不增加新的开奖方式、积分兑换、公开 Bot 指定中奖入口或独立网站。历史已确认邀请保留、不可变开奖快照、Inbox、Outbox、幂等键与 Worker 租约保持原语义。

## 3. 确定的业务模型

### 3.1 四类事实分开

| 概念 | 决定什么 | 配置与累计范围 |
|---|---|---|
| 成员与其他条件 | 是否加入全部参与群、关注指定频道、符合原有用户名/地区要求 | 沿用全部强制目标逐项核验 |
| 抽奖门槛 | 是否完成本场要求的行为，进入最终候选名单 | 邀请好友或发言数二选一，选定模式内部按配置群分别达标 |
| 每日发言加成 | 增加多少抽奖次数 | 独立开关、逐参与群、北京时间自然日 |
| 邀请加成 | 增加多少抽奖次数 | 独立开关、逐参与群、本场累计，不设累计上限 |

新活动必须明确选择一种行为门槛，再为该模式选择至少一个群并保存参数；未设置完整时预览显示缺项，不能自动替用户选择。两种门槛不能同时保存或同时生效，也不提供“邀请或发言任一完成”的混合规则。

加成有四种组合：全部关闭、仅每日发言、仅邀请、两者同时开启。两种门槛分别乘以四种加成组合，共八种基础组合必须验证。门槛模式不决定哪些加成可以开启。

```text
最终可参与开奖 = 成员及其他条件合格 AND 所选行为门槛达标
累计抽奖次数 = 已入账基础次数（0 或 1）+ 累计每日发言加成 + 累计邀请加成
有效抽奖次数 = 最终可参与开奖 ? 累计抽奖次数 : 0
```

基础次数在首次成员及其他条件核验通过时按原服务幂等发放一次。仅点击登记但条件尚缺时不展示已有基础次数。门槛未完成时可先登记、完成成员校验并累计加成，页面显示“已登记，门槛待完成”，加成暂存。门槛完成只改变资格，不凭空增加基础次数，也不重复发已存的加成。

个人状态依次展示“未登记 → 已登记，成员条件待补齐 → 成员条件已通过，门槛待完成 → 当前可参与开奖 → 已截止，复核中 → 已开奖/已取消”。成员条件后来失效或未知时回到对应资格状态，已完成的行为事实与历史奖励保留；门槛达标不等于最终复核通过。

新场只由本人明确登记动作创建参与意图。入群/关注事件可更新成员事实、推进已有登记的成员校验，但不能为尚未明确登记者自动创建Participant或发基础次数。这条覆盖现有[入群后自动登记](../../src/tg_lottery/telegram/member_flow.py)在V3.0上的行为；旧活动沿用旧版本规则。

### 3.1.1 统计起点与资格变化

- 首次明确登记保存来源Update与时间；首次成员及其他条件通过后保存本场计数启动时间/Update水位。重复登记、重新验证、退群重进均不重置起点或重发基础次数。
- 已启动统计的参与者继续记录相关来源事件，但记录不等于计数/计奖。发言计数仍须满足冻结合同中的成员及其他条件；缓存暂变PENDING或UNKNOWN时保留待复核事件，不直接丢弃或先行奖励。来源时点已证实不合格的发言明确记录拒绝，不推进门槛或新增加成。
- 后来通过成员校验不能证明先前离群期间合格，也不能自动回填该期间的发言。无法证明来源时点资格的事件保持待核验，不计达标；当前成员资格决定当前有效次数/开奖资格，已经取得的门槛与奖励事实按原合同保留。
- 获取新个人邀请入口仍实时复核本人及目标权限；已有入口的真实新成员归因、留存和确认按原规则处理。邀请人资格失效不撤回已确认人数/奖励，也不伪造其可开奖资格。
- 新场消息必须属于本场计数起点之后且在截止范围内。同一秒依来源Update水位判定先后，延迟/乱序消息不能因为处理较晚就被当成登记后的消息；事件日期仍按Telegram消息时间转换为北京时间。

### 3.2 发言数门槛

- 使用“北京时间每日有效发言条数”的现有基础门槛模型；逐群设置条数、每条最低有效字符数。支持 20、34 及其他自定义正整数，20/34 是数值示例，不是全局限制。
- 默认需要达标 1 天；保留原连续天数自定义。设置多天时明确显示“连续 D 天，每天 N 条”，不把“累计 N 条”写成“每日 N 条”。
- 各开启门槛的群分别完成，所有配置群均达标后本场行为门槛完成；未选为门槛目标的群没有发言要求。加入全部参与群的成员要求继续执行。
- 按 §3.1.1 的首次计数起点统计本期消息，不回填起点之前或机器人未观察到的历史消息；新活动不引用跨活动的全局累计次数。
- 某群完成完整周期后保留本场该群达标资格；后续午夜清零今日数、中途断日均不撤回已完成的本场资格。未完成完整周期时，断日重算连续天数。
- 多群不要求在同一天完成：A群周一完成、B群周二完成，只要均在本场截止前就总体达标。页面明确“本场完成一次即可；每日加成另算”，已完成群显示完成日期，不用今日0条替代已获资格。
- 每日门槛与每日加成分别按各自阈值及最低字符数判断。同一消息可以满足两套已明确配置的规则，但“加成完成”不代表“门槛完成”。

### 3.3 邀请好友门槛

- 逐参与群设置需要的有效新成员数 K，支持正整数自定义；各开启的群分别累计，所有配置群达标后完成本场门槛。
- 有效人数来自同活动、同邀请人、同目标群已经确认的 `Invitation.VALID`；刚打开链接、申请入群、待留存或无法核验均不算达标。
- 先登记并通过成员及其他条件，随后即可获取门槛目标群的个人邀请入口，**不要求先满足邀请门槛，也不要求开启邀请加成**。
- 门槛达标 K 人后继续记录后续有效人数；K 是获得资格的阈值，不是邀请人数的上限。开启邀请加成后继续按其独立规则加次数。
- 沿用真实新成员、首次归因、留存、截止与防重复规则。新活动不额外要求被邀请人完成发言任务，也不把邀请人自己的发言算作邀请人数；历史已冻结的受邀人活跃条件继续按旧合同读取。
- 同一人通过 A 群与 B 群的对应个人入口成为有效新成员，可分别贡献各群人数；同一群只首次归因一次。普通补齐成员条件的链接没有邀请归因。
- 确认后退群、链接过期/撤销不扣回已确认人数或已获邀请加成；邀请人自身退群影响其当前成员资格，与已获得的行为达标事实分开。
- 留存要求是本场共享的“有效邀请要求”，在邀请门槛或邀请加成任一开启时可见；页面同时显示报名截止、最晚有效入群和计划开奖时间。门槛与加成引用同一份有效人数，不能设置互相矛盾的留存口径。

### 3.4 两种独立加成

| 设置 | 每日发言加成 | 邀请加成 |
|---|---|---|
| 开关 | 逐群独立开启/关闭 | 逐群独立开启/关闭 |
| 数量规则 | 每天满 N 条获得 R 次；默认每天达标奖励一次 | 每 X 个已确认有效新成员 +1 次 |
| 时间范围 | 北京时间每天 00:00 开始新一天，历史奖励保留 | 本场有效邀请累计，跨日不清零 |
| 上限 | 保留现有每天一次/自定义每日轮数/每日不限，页面明示当前模式 | V3.0 新活动固定不设累计上限，不显示设置上限按钮 |
| 未达门槛 | 达标照常入账，显示暂存 | 确认照常入账，显示暂存 |
| 关闭其他模块 | 不受邀请加成开关影响 | 不受每日发言加成开关影响 |

每日发言加成的默认每天一次不是新增限制，沿用既有可选模式；不能因邀请不限而把每日发言也静默改为不限。邀请加成保存 `cap_mode=unlimited`、`max_bonus_tickets=null`，不能用大数字代表不限。旧活动的有限上限保持原值。

同一条有效消息可分别推进发言门槛与发言加成；同一份有效邀请事实可分别推进邀请门槛与邀请加成。门槛事件不写加成票，奖励事件只写一次票，不能为两个用途重复记账。

## 4. 创建者页面与多群配置

### 4.1 草稿预览入口

保留 `/new` 直达预览及未过期草稿恢复；预览提供清晰入口：参与活动的群、关注/加入条件、抽奖门槛、每日发言加成、邀请加成、开奖时间，其他奖品与说明入口沿用。

“关注/加入条件”只展示成员要求；“抽奖门槛”设置二选一模式；两个加成入口各自展示开启的群数。预览正文列出具体群、阈值和开关状态，不只显示“已开启”。

```text
🎟 抽奖门槛（只能选择一种）
[发言数] [邀请好友]
当前：发言数
A 群：每天 20 条，每条至少 4 个有效字符，需达标 1 天
B 群：每天 34 条，每条至少 4 个有效字符，需达标 1 天
C 群：不设置发言门槛
[选择/编辑群] [保存] [取消]
```

点击切换模式先展示新模式编辑稿和将替换的旧模式；保存时明确说明替换，原模式失效。取消保留原模式及参数，不把两套规则并列存进生效配置。切换门槛不改任何加成规则。存在未保存改动时离开页面沿用“放弃修改/继续编辑”；取消单项数字输入只取消该输入，不丢弃其他编辑值。

### 4.2 逐群规则表与保存语义

```text
群       本场门槛         每日发言加成           邀请加成
A 群     每天 20 条       每天 20 条 +1 次       每 1 人 +1 次，不限
B 群     每天 34 条       关闭                  每 2 人 +1 次，不限
C 群     不设发言门槛    关闭                  关闭
```

- 分别提供“移除本群发言门槛”和“关闭本群每日发言加成”，各自只改对应模块。若提供“关闭本群全部发言要求”快捷操作，须列出将移除的门槛与加成，确认后同时修改；不把通用“关闭发言”按钮绑定到两个隐蔽改动。
- 关闭最后一个门槛目标群后草稿明确显示门槛缺项，要求重新选择目标或切换门槛类型；不自动恢复规则，也不偷偷改成无门槛活动。
- 邀请门槛模式下，逐群规则表改为邀请人数门槛；可给部分群开启每日发言加成，二者各自显示。
- 未开启某项的群不进入该项达标判定，不使用最低群进度合并所有群，也不把其他群消息挪到当前群。
- 新增参与群默认不设置该群行为门槛、两种加成均关闭；创建者在预览核对是否要把它加入门槛目标。成员加入要求仍包含全部参与群，页面不能把“无行为门槛”解释为“不必加入”。
- 配置草稿采用编辑稿，保存后生效；返回/取消不保存。自定义非法输入保持旧值，明确说明错误。
- 每页沿用 6 项及分页/搜索/刷新。规则行包含群名；频道只支持关注条件，不提供发言门槛/加成。
- 复制设置沿用现有“复制到选定群”；正文列出来源、目标与被覆盖项，未选群保持原值。复制一种模块不覆盖另一种。
- 移除群时说明其关联配置；只清理该群未发布配置。删除额外关注条件不能清空其他参与群的门槛与加成。
- 保存和发布前核验创建者、机器人及对应功能权限；发言目标需允许普通成员发言，邀请目标需可创建邀请链接。错误列出具体群和原因。
- 本场规则发布时冻结。普通创建者编辑只作用于未发布草稿，不能给运行中活动临时降低门槛或改变加成。

邀请模式页面提供“有效邀请要求”入口，发言加成页只编辑每日发言奖励。选择邀请门槛后打开留存页，返回邀请门槛；从邀请加成打开则返回邀请加成。群规则复制、载入上次或模式切换都必须在新发布预览中列出最终门槛与加成，不能因页面来源丢失共享邀请要求。

## 5. 条件文本、链接与前置落地页

### 5.1 统一展示合同

群活动卡、创建最终预览、发布回执、长按转发内容、活动链接落地页、完整规则页使用同一冻结规则投影，按“成员条件 → 行为门槛 → 额外加成 → 时间与参与入口”排列。

每个强制条件都包含动作、群/频道名称、具体要求和可点击入口。公开群/频道显示合法公开链接；私有目标在公开消息中显示本活动的机器人访问入口，进入现有授权私聊流程后提供实际加入链接。不把加密私有链接直接散布到公开卡、日志或审计中。


邀请模式同一位置改为“本场门槛：邀请好友；A 群有效邀请 K 人、B 群有效邀请 M 人”，不显示发言门槛；若开启每日发言加成，仍在额外次数段展示。

有效消息说明展示最低有效字符数、文本/非空图片说明、命令/机器人/服务/转发/纯符号不计、重复文本规则及本场统计起点。旧累计门槛保留“累计发言”及其原最低字符数/去重口径，不套用新每日规则。

### 5.2 打开活动链接后先看条件

1. `join_<活动ref>` 先展示上述活动及条件，再提供“登记并验证条件”按钮；查看规则不自动发票、不声称报名完成。首次打开 Bot 所需的 Telegram 原生启动步骤保留。
2. 点击登记后沿用幂等 Participant 与成员校验。成员合格但行为未达标时显示“已登记，完成门槛后可参与开奖”，并直接提供本场发言进度或门槛邀请入口。
3. 已登记者重新打开，展示同一活动的本人进度与未完成项；重新验证不重复登记、发基础次数或归因。
4. “规则”“分享”“加入入口”必须返回同一活动，不能因按钮/链接入口不同而看到不同版本的要求。个人邀请入口保留活动、邀请人与目标群绑定，点击本身不作为真实入群事实。
5. 截止、取消、开奖后先显示真实状态与历史规则，不引导用户继续完成本期任务。截止关闭新登记及新来源行为入口，截止前事件仍按原合同排空、复核；取消/开奖终态不继续计奖。

个人邀请落地页同样展示活动条件，并写明此邀请用于“完成邀请门槛”“增加邀请加成”或“两者”；仅门槛时不能写“会增加抽奖次数”。受邀人只需按该目标群的有效新成员/留存规则核验，不要求先完成自己的抽奖门槛；真实入群不自动替其登记抽奖。页面提供独立的“查看条件并登记本场抽奖”，不改变原邀请归因。

完整条件不可因超过三项而被替换为数量摘要。长文按完整语义项分页，显示总项数/页数和下一页入口；全部条件仍可读，资格核验覆盖完整集合。

有封面且完整正文超出当前图片说明容量时，公开显示简明摘要，并通过同一次发布的独立完整规则文字消息展示所有条件与链接；卡片与规则消息分别记录投递结果。无封面时使用完整文字或连续规则页。不能截断要求后声称“条件已完整展示”。

需要独立规则消息时，先逐群确认规则消息并保存其远端消息ID，再投递含对应规则入口的卡片；同一参与群所有必要消息都确认后才算该群发布完成。任一必要消息失败或结果未知时沿用发布Saga的未完成状态，不以卡片单独成功关闭发布。

完整规则在发布前冻结成逐群有序页清单，并预先校验文字、链接和封面说明的渲染长度；每页拥有独立投递键/回执，不拆开HTML链接或单条条件。发布重试只补明确失败的未确认页，UNKNOWN先对账。取消、截止、开奖后所有已确认规则页同步标记活动状态并关闭报名引导；旧转发仍由同活动落地页显示当前状态，不删除历史规则。

## 6. 达标提醒、个人进度与失败反馈

### 6.1 通知矩阵

| 事件 | 触发与投递 | 必须展示 |
|---|---|---|
| 某群当天发言门槛完成 | 尚未完成该群完整周期时，第一次跨过当日阈值，在对应群提示 | 活动、群、北京时间日期、N/N 条、连续 D/D 天、本群是否完成 |
| 某群邀请门槛完成 | 有效邀请确认并跨过 K，在对应群提示 | 已确认 K 人、待核验人数、本群完成状态 |
| 全部行为门槛完成 | 最后一项完成时，在该事件对应群发一条活动级提示 | 所选模式已完成；其他条件未通过时仍明确不能参加开奖 |
| 每日发言加成入账 | 每次目标奖励增加，在对应群提示 | 今日进度、本次 +R、今日/累计奖励、生效或暂存 |
| 邀请加成入账 | 确认有效后产生正向奖励，在对应群提示 | 有效人数、本次增加、累计奖励、不设上限、生效或暂存 |
| 旧累计发言门槛完成 | 已有报名尝试的用户跨过旧门槛时提示 | 累计数、对应群已达标、仍需重新验证的其他条件；不伪装成每日任务 |
| 连续天数中断 | 未完成门槛者断日后再次有效发言 | 重启进度，历史加成保留 |
| 截止仍未达标 | 排空截止前事件、完成资格复核后发一次本场说明 | 本期不能参与、未完成项、累计奖励只保留记录 |

必要状态提醒沿用 Outbox、用户 ID 提及、正文转义和开启通知，不受扩展提示开关关闭。某群完成就提示该群；全部门槛未完成不应压掉局部成功提示。个人私聊进度可查询所有群与事件，不因群通知失败而隐藏真实业务完成事实。

同一来源事件在同活动、同用户、同目标群同时产生本群门槛任务完成、全部门槛完成和加成入账时，合并为一条完整提示；发言和邀请都遵守此规则。payload保留各事件引用，各项业务事实分别幂等。通知统一在本次事务的门槛/账本更新完成后构建，避免三连提醒或先显示旧次数。不同群、不同日期或不同来源事件不合并；活动级门槛完成只记录/提示一次。

已完成本场门槛后不再每日重复要求完成门槛；仍可展示今天发言数，开启的每日加成继续正常提醒。延迟送达的通知标明事件日期及“完成时”的次数/资格，不把过去达标冒充发送时仍可开奖，查看进度返回最新状态。

### 6.2 幂等、事务与异常

- 以 `before < threshold <= after` 判断首次跨越，并配合唯一事件/达标键；不能只依赖“计数恰好相等”处理并发或补处理批次。
- 业务事件键至少区分活动、参与者、目标群、事件类型；每日事件再包括北京时间日期，加成再包括账本目标/轮次。同来源合并通知键关联这些事件；重放不重建不同内容的同键通知。重放 Update、重启 Worker、重复验证均不重复加票或重复发完成提醒。
- 业务完成与通知意图同事务提交；若没有通知意图须暴露断点，不能用私聊即时发送掩盖群 Outbox 缺失。
- 通知文案使用本次事务最终的门槛和奖励状态，并随业务一同提交；不能在奖励生效前写“已经可以参加”，不能让用户自行猜暂存是否生效。
- 明确区分通知待投递、已确认、失败、远端结果未知；失败保留原因，未知走原对账机制，不静默改为成功或盲目重发。
- 未登记者的新每日行为不补采；页面先说明统计起点。旧累计门槛已在进入报名时满足的，应直接显示达标，不要求用户多发一条才能看到成功。
- 客户端的弹窗/声音与机器人发送成功分别验收；不能承诺绕过 Telegram 用户通知设置。

## 7. 时间配置与活动复用

- 保留直接进入时间输入页、`YYYY-MM-DD HH:MM` 自定义输入、可点选复制的文本与返回草稿。
- 保留“7天后”“10天后”“明晚20:00”；输入、快捷计算和展示统一使用 `Asia/Shanghai`。已保存活动的展示变化不改变其开奖时刻。
- 沿用开奖时间必须晚于当前时间 5 分钟；格式错误、日期不存在、时间过近分别说明，失败不覆盖旧值，发布时再次校验。
- 保留“载入上次抽奖”：复用标题、封面、奖品、成员条件、所选门槛及逐群参数、两种加成、领奖设置等允许字段，重新核验权限。
- 新草稿保留独立草稿身份；旧 Campaign ID、Participant、计数、账本、归因、个人邀请链接、Outbox、远端消息 ID、开奖任务和快照均不复用。
- 载入后清空旧具体开奖时间并提示“请设置本场开奖时间”；保留其他规则。不会以旧时间自动改成当前时间来让发布通过。
- 载入没有新门槛类型的历史配置时，列出旧发言条件并要求创建者选择一种新门槛，原活动保持原合同。历史有限邀请加成导入新草稿时明示新场改为不限，在保存/发布核对中呈现差异，不静默改写原活动。

### 7.1 三个时间与门槛可完成性

现有[时间构建](../../src/tg_lottery/telegram/draft_config.py)使用“报名截止 = 计划开奖时间 − 5分钟结算窗口”。正文同时显示两者；新登记、发言与邀请按截止判断，不能向用户承诺可以一直做任务到开奖时刻。

- 邀请最晚有效入群 = 报名截止 − 留存小时数；入群恰在该时点、留存恰在截止完成可核验，晚于它的入群不计本场。到边界仍未确认者显示待核验，实际处理可延后但不能跳过核验。
- 多天发言门槛按北京时间自然日判断。发布当天可算第一天，所需第D天必须落在截止范围内；不新增每条消息间隔或必须满24小时的隐含要求。
- 时间编辑后展示门槛最早可能完成日期与邀请最晚有效入群时间；保存门槛、发布确认和实际发布均复核。截止前根本无可完成窗口的配置明确指出冲突并要求调整时间/天数/留存，不自动降低规则或改期；这属于业务可完成性校验，不增加任意安全余量。
- 发布可完成性校验针对全部强制门槛群。仅可选邀请加成来不及完成留存时明确提示本场无法获得该加成，可由创建者保留；不能因此阻止本来可完成的发言门槛活动发布，也不能缩短留存制造奖励。
- 发布多群消息耗时后，以全部必要消息确认的实际时点重新核对剩余窗口。已无法开始且完成门槛时不得转为“进行中”，保留发布问题并可取消；截止时刻不因投递延迟而顺延。
- 截止前晚登记但已不可能完成的新用户，页面说明缺少的时间窗口，不承诺能够达标；已达标用户仍可按原截止规则复核。加成是否暂存、最终能否开奖分别展示。

例：10月10日20:00开奖，19:55截止；留存24小时的有效邀请最晚需10月9日19:55入群。10月10日才发布邀请门槛并保留24小时留存，属于不可完成配置。

## 8. 推荐实现与数据合同

### 8.1 用显式门槛模型表达二选一

在冻结 `CampaignRules` 中增加 `participation_rules_version=v3.0` 与判别联合 `admission`：

```json
{
  "participation_rules_version": "v3.0",
  "admission": {
    "type": "message",
    "groups": {
      "<A群ID>": {"daily_messages": 20, "consecutive_days": 1, "min_text_length": 4},
      "<B群ID>": {"daily_messages": 34, "consecutive_days": 1, "min_text_length": 4}
    }
  }
}
```

邀请分支为 `type=invite`、逐群 `required_valid_invites=K`；与发言分支参数互斥。服务端保存、发布和读取均验证模式/参数，不只靠隐藏按钮保证二选一。所有目标属于当前参与群，新活动不同时写旧 `message_thresholds`/`base_activity_rules` 作为另一份生效门槛。

使用规则内产品版本区分新门槛，保留现有 `Campaign.contract_version=v2.4` 的多群/开奖承诺结构语义，不能只换成 `v3.0` 而让当前合同识别函数退回单群或丢失承诺校验。

### 8.2 资格与进度

- 新增 `Participant.admission_qualified`，V3.0 有门槛的登记初始为 false；历史行迁移默认 true，历史资格仍使用其原 `base_qualified`/累计门槛合同。
- 增加明确登记意图及首次计数启动时间/Update水位；`created_at`、页面查看时间或重试处理时间不能代替。事件接收加载已启动的Participant后逐模块记录/判定，不能只按当前成员缓存为ELIGIBLE筛掉原始事件；被记录事件只有满足计数条件才推进进度，未知资格显式待核验。
- 新增逐群 `AdmissionProgress` 达标事实，唯一身份为活动、参与者、稳定的参与群记录ID、门槛模式，保存规则 revision、达标时间及来源事件引用；群升级后不因chat ID变化丢进度。累计视图引用原消息/邀请事实，不复制第二份票账本。
- 发言门槛复用有效消息判定、BaseActivityEvent 的逐日事件与连续计算，在新版本读取新门槛规则；邀请门槛消费确认邀请事实，不依赖邀请奖励函数是否执行。
- 成员资格保留 `qualification_state`，行为门槛使用独立字段；登记、查询、最终资格复核、人数统计、结算及快照过滤统一调用同一按版本解释的资格服务。
- 新活动最终快照需同时满足成员资格与行为门槛，最终权重仍来自追加式票账本；不能只给页面加门槛而让开奖继续只检查旧字段。
- V3.0资格服务只解释新门槛，历史资格服务继续解释旧门槛；查询投影、缓存与最终数据库筛选均遵守这一分支，不能把历史行默认的 `admission_qualified=true` 当成跳过旧门槛的依据。
- 旧累计门槛提醒从其原统计事实出发，修复重放计数与达标意图的事务/幂等关系，不改写旧活动计数口径、不扫描补发全部历史群通知。

### 8.3 事件分发与邀请入口

- 以相关活动目标集合分发消息，再分别判断发言门槛、发言加成、旧累计门槛及历史受邀人活跃任务；同群多活动逐个处理，所有配置目标均被覆盖。
- 关闭每日发言加成不移除发言门槛的路由，开启其他群的加成不移除本群门槛路由；不存在配置规则的模块不计奖。
- 有邀请门槛或邀请加成的群均可创建本场个人邀请入口；邀请码创建、归因、确认、记录查询和结束隐藏均基于二者并集。
- 留存设置由“有效邀请要求”管理，门槛与加成引用同一份确认事实；即使邀请加成关闭也能编辑留存。新场不启用旧 `require_activity` 耦合，导入存在该旧要求的配置时说明差异，旧活动仍按冻结值核验。
- 邀请确认后，在同一业务事务分别更新门槛达标事实、奖励差额，再按§6生成合并或独立通知意图。计数来源必须包含正在确认的那笔邀请且只包含一次，兼容当前奖励计算先于写入 VALID 的顺序。
- 新旧同群活动使用各自冻结版本；不能让 V3.0 的路由或开关改变旧活动的计奖规则。

### 8.4 实施落点

## 9. 完整功能测试与便捷验收

### 9.1 八种基础组合

| 门槛 | 加成组合 | 必须断言 |
|---|---|---|
| 发言 | 全关 / 仅发言 / 仅邀请 / 两者开启 | 发言门槛独立完成；无关模块不计奖；加成前后资格/权重正确 |

每种组合覆盖草稿保存 → 发布 → 条件前置 → 登记 → 未达标 → 达标 → 截止复核 → 开奖快照 → 两群结果公告；有中奖者时继续核对中奖私信。自动化和真实Telegram结果分栏记录，无人达标场景不能为完成流程而降低门槛或伪造中奖者。

### 9.3 让测试方便的实现方式

采用可复用的自动化场景数据与真实测试活动配置，不在业务代码增加测试捷径。测试配置使用正常自定义：发言2条、邀请1人、达标1天、留存立即核验，便于快速验证端到端；20/34条边界与24/48小时场景仍单独覆盖，不能用简化配置替代。

- 自动化用固定事件时间和受控时钟覆盖跨日/留存，不等待真实24/48小时；必须走真实领域、数据库、Inbox/Outbox处理。测试替身只表示可控外部响应，不作为Telegram送达证据。
- 数据库测试经上海Docker执行器，迁移与测试同一专用库，身份检查先于清表；后端每个进程硬超时60秒，全量八分片由`flock`串行执行。路由见[上海测试环境](../deployment/SHANGHAI_TEST_ENV.md)。
- 新测试按职责分组：门槛XOR、逐群发言、邀请准入、独立加成、条件投影、最终开奖；定向验证后跑现有完整回归及迁移往返。
- 真实验收使用独立测试Bot、两个参与群、一个额外群/频道、至少两名参与者和可确认新成员身份的受邀账号；实际使用的群、人数与身份不足时对应项标“未验证”，不能关闭规则通过。
- 真实流程可通过“载入上次”复用两种门槛的测试配置，但每场仍用新活动/链接/计数；测试保留期或新成员身份未满足时明确记录原因。
- 邀请实测准备按场景可用的新成员账号或新的测试群，不能清除群成员历史把老成员伪装为新成员；同一群/账号的重复使用只作为老成员、重进和重复归因的反例。真实24/48小时留存需完整等待并取得观察事实，快速配置与自动化时钟不能替代该项实测。
- 自动化应覆盖本项目现有创建、封面、准入、配置、分享、登记、邀请、发言、截止、开奖、结果回查、通知、取消/归档、权限与旧面板恢复。真实验收逐项列证据，不用“全量通过”代替未实测功能。
- 每个组合/专项用例记录前置条件、操作、期望事实、实际证据和结果；明确区分“不适用”“失败”“未验证”。无中奖者时私信不适用，私信发送失败则为失败；不得把两者混为跳过。按场景逐项关闭验收，无需把所有专项与八组合机械相乘。

## 10. 迁移、发布、回滚与完成标准

- 迁移只新增新规则所需字段/表，历史行为按显式版本读取，不将旧群累计门槛改写成每日门槛，不自动赋予旧活动邀请门槛。
- 新规则首次发布前有完整迁移往返与历史兼容证据；存在新规则活动时，有损降级明确拒绝。应用回滚先验证旧版本能否读取/处理新活动，不能直接回退后让新活动按无门槛开奖。
- 仅在JSON增加产品版本不能保护回滚：[当前规则模型](../../src/tg_lottery/domain/rules.py)并未拒绝所有未知字段，[当前回滚脚本](../../deploy/rollback.sh)也没有规则能力检查。实施须在发布/回滚合同与执行器中核验目标制品支持的规则版本及数据库中的待履约活动；不兼容时保留现有可履约版本并明确失败。支持该检查的兼容版本才可成为启用V3.0后的回滚目标，不能用迁移或健康检查成功替代。
- 发布沿用[部署合同](../deployment/DEPLOYMENT.md)的`master → release → GitHub Actions → GHCR → 生产服务器`，版本、镜像、迁移与进程状态单独核验。
- 生产未决投递按现有对账机制处理；不为验收清队列、补写成功、盲目重发、修改旧开奖快照或触发未授权真实开奖。
- 验收记录至少包含代码SHA、规则版本、活动/用户/群/时间窗口、消息事件、资格/门槛状态、账本、Outbox/Attempt、Telegram消息ID及客户端截图。通知客户端声音另列范围。
