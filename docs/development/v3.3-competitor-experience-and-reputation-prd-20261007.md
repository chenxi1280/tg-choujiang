## 1. 为什么此前对标没有补全

仓库记录显示，问题不是没有见过竞品人品能力，而是将机制差异当成既定产品范围，后续没有重新检查它是否满足用户要求：

1. [V1.8 §4.4](v1.8-lotterybest-repair-prd.md) 已提出独立人品账本、兑换、查询、排行、管理员加减分，当时计分参数仍是 TBD。
2. [V2.0 §1](v2.0-lotterybest-parity-redesign.md) 与 [V2.2 §9](v2.2-configurable-participation-bonus-prd.md) 后来排除了长期积分和排行，采用本场邀请/发言直接加票。V2.0 文档称其为既定决定；本轮没有重新取得该决定的原始用户授权证据，不能据此认定用户接受当前缺失。
3. [2026-09-05 深度对比](lotterybest-deep-comparison-20260905.md) 明确记录了竞品逐群兑换成本、同时扣多群积分和额外票上限，但把它们标为“机制不同”，未进入完整交付矩阵。
4. [公告合同](message-card-style-20261005.md) 写了可点击群名、逐群门槛，却没有把公开/私有、缺链接、长卡、转发、对应群的实际加入与条件反馈逐项作为客户端完成门槛。
5. 当前源码 `bonus_block` 把邀请/发言直接加票放在“人品加成”标题下，进一步造成用户按名称期待积分兑换。

纠正原则：每一项竞品可见能力都应记录“需求来源、我们的目标、源码现状、差异理由、完整路径、验收证据”。只有明确排除并说明影响，才可以保留差异；不能自行把已有替代机制视为等价满足。

## 3. 必须明确的产品边界与设计建议

以下四项是本稿的**推荐方案，待用户审阅，不声称已确认**。源码实现前须采用已确认的版本，不能在代码里默选另一种业务语义。

| 决策 | 推荐方案 | 原因与影响 |
|---|---|---|
| D1 人品与直接加票关系 | 新活动“加成设置”选择：关闭 / 现有邀请与每日发言直接加票 / 人品兑换；后两种互斥，人品模式默认上限9、可配置1–9 | 否则一面宣称“额外最多9”，另一面无限邀请加票，规则失真；邀请作为硬门槛仍可使用，不自动发奖励票。历史直接加票活动继续原规则 |
| D2 哪些群参与扣分 | 创建者从本场必须加入的群聊中选择成本群；启用时至少一个群，每个群必填非负整数成本，频道不设人品成本；0是合法成本 | 逐群扣分；未配置群与成本0的群不同，规则页都要说明；纯频道活动不能开启人品兑换 |
| D3 私有加入链接呈现 | 默认群名进入“本场×本目标”的稳定 Bot 入口，再显示对应私有加入按钮；创建者可明确选择“在公告公开加入链接”，启用后正文直接到该私有群/频道 | 保留现有不默认泄露私有邀请的约定，同时让每个群名有明确目标。公开私有链接会随分享传播，选项须在预览可见；不能用整个活动首页掩盖目标 |
| D4 取消与资格变化后的积分 | 活动正常开奖、未中奖或个人后来失去资格不退消费；活动在开奖快照前由创建者取消时，自动按原兑换单完整退回全部消耗 | 避免逐用户退群套利；活动取消由组织者负责。补偿只追加，失败保留待退款及原因，不提前显示已到账 |

已由用户本轮给出的目标参数：人品消息超过3字 +1、每用户每群自然日最多30、每个配置群单独成本、兑换一票同时扣各群、额外上限9，以及五个中文指令。竞品未说明的字数归一、排行口径、去重窗口、全0成本、退款、管理员原因流程等，均是本稿补充设计，不能反向称为竞品实测结论。

V3.1 的门槛/每日加票“短文字和媒体可计数”保持；人品“超过3字”是另一条独立统计通道。公告统一：直接加票模式叫“抽奖加成/额外抽奖次数”，只有真实余额消费模式叫“人品加成”。

## 4. 公告、链接与完整条件

### 4.1 每个目标就是一个完整条件块

所有必须加入的参与群、额外准入群和频道均取同一冻结目标清单；以稳定目标身份去重，保留展示顺序。展示名称、类型、普通加入入口、本群门槛，不能只列群名或默认用主群条件替代所有群。

```text
📮 参与条件（必须全部满足）：
🎫 加入-[A群]                  ← 群名可点击到A
└ 🎟️ 本场单日有效发言满20条     ← 若真实规则为单日20
🎫 关注-[B频道]                ← 直达B，频道没有发言条件
🎫 加入-[C群]
└ 🎟️ 连续3天，每天有效发言满5条 ← 仅真实配置时展示
```

竞品样例“发言数大于20条”的数学边界是21条；现有合同“满/至少20条”的边界是20条。保留我们已冻结的包含边界，不为了复制文案改变资格，也不把两者混写。历史累计门槛必须写“累计”；无门槛的群不生成虚构缩进行。用户名、地区、登记后统计起点、截止另行可见；频道只展示关注要求。

### 4.2 链接与权限状态

| 目标状态 | 正文/操作行为 | 不能误表示的事实 |
|---|---|---|
| 公开且有确认地址 | 正文群名、条件页打开按钮直达对应群/频道 | 普通加入不记邀请归因、不自动报名 |
| 私有、采用目标入口 | 点击名称后首屏就是对应目标名称、条件与加入按钮；保留回同活动来源 | 不再打开整场无定位首页，不暗中登记 |
| 私有、创建者选择公开地址 | 群名直接打开已确认的普通邀请；仍加密保存，不写入日志和文档 | 这是经选择向公告受众披露链接，不等于可公开所有密钥 |
| 邀请申请待批准 | 展示“等待管理员批准”，能刷新核验 | 申请成功不是已经加入 |
| 地址未知/创建失败/撤销 | 明示具体目标与状态，给刷新/返回；创建者看到权限或投递问题 | 有超链接标签不代表入口可用，不能换成错误目标 |
| 截止/结束 | 显示历史条件，参与与兑换入口关闭；普通目标导航是否保留取现有生命周期 | 不复活报名，不撤销原本需要持久保留的个人邀请路由 |

地址刷新可更新同目标的入口可用性，不改变已冻结的群身份、门槛、成本与计数起点。普通入群地址、人品查询入口、本场个人邀请计奖入口是三个不同动作。组合文件夹只作辅助，仍逐项核验。

Bot 接收普通群文字需要具备消息可见条件；Bot 管理员或关闭隐私模式时能接收普通用户群消息，开启隐私模式时不能假设这些关键词都会送达。[Telegram Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get)。本项目启用群统计前检查并展示权限准备状态，不用“0人品”掩盖未观察到消息。

其他用户的成员核验依赖 Bot 管理员权限保障；创建邀请链接还需要相应邀请权限。API错误保留“未知/待核验”。[getChatMember](https://core.telegram.org/bots/api#getchatmember)、[createChatInviteLink](https://core.telegram.org/bots/api#createchatinvitelink)。

### 4.3 长文与转发

- 首先保留完整条件块，再考虑奖品和长说明分页；不能一超长就删除全部条件，只留“查看规则”。
- 图文说明装不下完整条件时，采用封面消息 + 紧邻的条件续页 + 主操作消息的原生消息组，页码、活动名和同活动链接在各页可见；条件块不可拆开，单块也超限则发布前提示调整。
- 发布预览同时展示实际消息组结构；“分享活动卡片”向本人发送同样完整卡包，并提示多条需一起转发。每条都保留同活动规则/参与入口，单独转发某页仍能回查全部条件。
- 能放下一条时仍采用单条卡片，不增加中间步骤；长文消息组须逐条确认，全部必要消息确认后才标完整发布。消息组非原子远端操作，部分成功、失败及 UNKNOWN 分开显示与对账。
- 正文群名、缩进门槛、各页链接、主按钮和个人条件页都来自同活动同 revision 投影。群名称转义、同名群辨识、HTML容量检查继续保留。

## 5. 人品积累规则

### 5.1 账户、启用与日上限

人品属于“Bot租户 × 稳定群身份 × Telegram用户”账户，跨该群的不同活动保存；A群余额不能抵B群成本。每日上限是每用户每群30，不是整个群全员共用30，也不是所有群合计30。活动报名不是平时积攒人品的前提：群管理员启用后所有可观察到的真人群成员均可积攒，启停时间及规则revision可审计；群页面可查启用状态和起点。

上线默认未启用，管理员在“群人品设置”明确开启，并看到消息观察能力。关闭获取只停止新增消息积分，保留查询、消费与已承诺活动；暂时失去消息权限明示统计暂停与最后可靠时间。群升级需将新旧 chat ID映射到同一稳定群账户，不重置或复制余额；历史事件仍保留原 chat ID。

按消息原始时间归属 `Asia/Shanghai` 自然日，00:00只重置当日获取计数，不清空余额。可靠消息通过Inbox延迟处理仍归原日，日上限按事务原子执行；启用前、关闭期间和Bot未收到的消息不补造积分。余额与日获取值必须可由账本重建，后台重建不能回放Telegram写操作。

### 5.2 独立的有效消息判定（推荐补充口径）

1. 真人本人在启用群发送的原创文本；机器人、服务消息、转发、匿名管理员/频道代发、查询/管理指令、斜杠命令不获分。
2. Unicode归一后统计字母、汉字与数字，空白、标点、emoji、组合附加字符不单独算字；严格 **超过3个可计数字符，即至少4个**。3/4字边界必须有样例。纯图片/贴纸/GIF/表情不获人品；媒体附文仅在附文本身达标时可获1分，一条Telegram消息最多1分。
3. 同用户同群5分钟内归一后的相同文本只计第一条；大小写及空白归一。不同群独立去重。该5分钟是我们的防刷建议，非用户提供的竞品事实。
4. 相同 `(群,message_id)`、重复Update、处理重试最多+1；编辑不补分、删除不自动回扣，避免反复编辑/删除套利。达到30后继续聊天不获分，查询仍能看到30/30。
5. 同一消息可以按 V3.1 计入已登记活动门槛，并独立按人品口径获分；两条账都必须分别满足前置条件。指令先路由返回，不应被任一统计通道算作聊天。

余额为累计获取 + 管理员加分 + 退款 - 管理员扣分 - 兑换消费；管理员加减、退款不占自然消息日上限。消费后当天不能重新获取超过30；上限控制“获得量”，不是当前余额。

## 6. 创建者设置与发布路径

草稿预览 → 加成设置 → 人品兑换 → 配置每人额外上限 → 选择成本群 → 逐群填每票成本 → 保存 → 预览 → 发布前校验。

- 新人品模式默认关闭；打开后上限默认9，可选1–9。关闭保留当前草稿工作副本，恢复时重新校验；取消输入不丢原设置。切换模式明确提示停用另一模式，用户确认后才变更，不能 silently 保留隐藏奖励配置。
- 成本不能靠猜测给默认值；A100/B50/C0是规则示例，不作为所有活动默认。输入成本接受0，拒绝负数、小数、溢出和无效格式；具体存储安全上限在实施设计中确定并在输入页显示。
- 所选成本群须是本场必须加入的群，创建者具备当前配置权限、群人品已启用、账户能力可用。移除成本群前提示影响并确认，回到未发布草稿；已发布活动不允许改成本或票上限。
- 全部成本为0时预览必须说明“免费领取额外票，仍受本场上限”；不做除0计算，不自动发9票，仍需本人兑换确认。存在正成本时显示扣分所需的所有群。
- 频道可作为必须关注条件，但没有消息人品账户，不出现在成本选择器；仅有频道的活动不提供人品开启选项，并说明原因。
- 复用上次配置只复用可编辑规则；重新核对群、权限、启用状态、成本和上限，不复制用户余额、兑换单、历史票或旧活动路由。
- 最终预览同时展示具体群名/加入入口/基础条件、人品上限与成本、计数口径、截止、开奖和退款规则，保存成功后重新进入同一草稿。

## 7. 参与者兑换路径

活动条件 → 明确登记 → 满足本场成员及行为门槛 → “人品加成” → 查看逐群余额/成本/缺口 → 选择1至可兑换最大值 → 确认消耗 → 展示结果与明细 → 返回本场活动。

人品查询与规则查看不报名、不扣分；加入群本身也不启动本场门槛统计。推荐仅允许已登记、所有资格满足、活动开放且未过截止的人兑换；未达标可以查看余额和缺口，给对应群加入/门槛入口，不先扣分等待资格。

### 7.1 多群消耗的准确语义

每兑换1票，都要同时扣所有配置成本群，不是任选一个群，也不是分别兑换后相加。例如A余额250、成本100；B余额120、成本50；C成本0：最多兑换2票，兑换2票后A50、B20、C不变，本场增加2票。任一正成本群不足则整个请求失败，各群余额及票账均保持原值。

最大可兑换数为本场剩余额外上限与各正成本群 `余额 ÷ 每票成本` 向下取整的最小值；所有成本为0时只看剩余上限。确认页展示每群扣分前/后值、兑换票数、本人本场已兑换/最多/剩余和活动截止。

### 7.2 确认、并发与失败

- 确认事务内重新核验活动状态/截止、可用资格观察、规则revision、兑换累计和各群余额；未知资格不能当作通过。远端核验有观察时点，开奖前仍按既有机制复核，不能承诺检查后永不退群。
- 多群按固定顺序加锁，账户扣分、兑换单、票账及通知Outbox同事务提交；同用户多活动同时兑换共享账户锁，余额不得透支，同场累计不得超过配置上限。
- 同一确认业务键重试返回同一兑换结果；同一旧确认页不能重复扣分。另一次合法兑换需要新确认与当前余额；确认token绑定用户、活动、revision、数量和有效期。
- 余额变化、到期、暂停、资格不满足或未知均返回具体原因，保留刷新/返回，不显示成功。事务回滚没有“部分群已扣”的成功状态。
- 本地消费已提交而Telegram回执未送达：私聊显示/刷新“兑换记录”读取原事实，Outbox未知按现有对账处理，不重新消费。显示“兑换完成”和“通知已送达”是两个事实。
- 截止、结算、开奖、取消后不再兑换；暂停时保留记录并说明暂不可兑换。正常未中奖不退；退款采用 D4，不改变历史开奖快照。

## 8. 群友查询与管理员操作

### 8.1 群友指令

| 输入 | 回复内容 | 边界 |
|---|---|---|
| 人品 | 回复输入者：本群余额、今日消息获得/30、启用/暂停状态、统计起点或最后可靠时间 | 不选最新活动、不汇总其他群、不只回一个无法解释的数字；无账户显示0及起点 |
| 人品排行 | 本群当前可消费余额降序，前10名、查询者名次、翻页、更新时间 | 推荐按余额排行；消费后名次可能下降，规则明确说明；正余额账户参与，无结果有退出 |
| 人品规则 | 超过3字+1、每日30、去重、积分保存、各活动成本/上限另定、管理员调整与退款说明 | 统一全群积攒规则；活动成本不能用群通用规则页替代 |

精确匹配上述文本并允许首尾空白，不因聊天中包含“人品”二字触发；错误格式给对应说明。查询在原群、原话题线程回复真人用户；人品排行默认不泄露其他群账户。分页按钮只读取该群，绑定来源身份与群权限；并列余额用同一显示名次，稳定用户ID排序只作翻页一致性。

当前是永久账户而非可取得全员名册的Telegram统计：排行覆盖本群存在余额记录、最近已确认仍属群成员的真人账户。已确认离群者保留余额但退出群排行；成员事实未知须标待核验、不给可信精确个人名次。不能把缓存成员身份说成刚核验全部群友。重新加入同群恢复原余额，不复制；不承诺所有群成员都曾被Bot观察到。

大群排行采用稳定数据快照分页、设置查询频率保护；被限流明确说明稍后再查，不吞掉输入。群查询与排行允许首次用户使用，不要求先私聊Bot。必要的个人兑换详情仍仅发本人私聊；私聊不可达时在群提示打开Bot的同场入口，不公开多群余额和成本明细。

### 8.2 管理员回复命令

| 输入 | 动作 | 必要校验 |
|---|---|---|
| 回复真人消息：加人品 100 | 为被回复用户的本群账户追加+100 | 操作者当前为本群群主/管理员、目标为明确真人用户、数字为正整数 |
| 回复真人消息：扣人品 50 | 本群账户追加-50 | 同上，余额至少50；不足则整个请求失败，不能静默扣到0或出现负余额 |

命令数字0、负数、小数、缺回复对象、回复机器人/频道代发、私聊执行、权限未知均明确拒绝并给正确样例。匿名管理员没有可靠真人操作者时要求切换个人身份，不根据消息显示名授予权限。撤权后的重复请求重新检查，不能只读旧 `GroupAdmin` 缓存授权。

保留“回复用户 + 数字”的便捷入口，同时满足旧V1.8原因审计要求：推荐管理员可在数字后附原因；未附时先进入补填原因页，填完展示目标/群/金额/原因并确认再写入，原命令本身不提前成功。理由页仅原操作者可确认/取消，过期不修改余额。这是我们的审计补充流程，不声称竞品具有该步骤。

写入前记录原余额、delta、结果余额、操作者/目标Telegram ID、群、UTC时间及北京时间展示、原因、原消息/Update身份与唯一业务键。加分不限制为30，30只限制自然消息获取。重放原消息不重复调分；后来再次发出的新命令是独立业务请求。回复结果绑定原命令，并通过Outbox投递；管理员调整不直接写抽奖票、门槛或中奖指定。

## 9. 公告与个人页面文案

公告人品区示例（A100/B50/C0，每人最多3额外票）：

```text
🔋 人品加成：⚡️⚡️⚡️  [规则]
└ 每人本场最多兑换3张额外抽奖票
└ 每兑换1票：A群100人品 + B群50人品 + C群0人品
```

闪电数量代表本场支持的最多兑换次数，不代表个人已兑换。最多9时显示9个或“⚡×9”，无论展示形式都写明确数字。群共用卡不展示“你已兑换”，不能根据发送卡片的人显示私人余额。闪电与“规则”都进入本场冻结规则；群通用人品说明是页内另一个入口，不链接竞品频道来冒充本项目规则。

个人加成页必须区分基础票、人品兑换票、当前有效总次数；不能把1+9额外写成“共9票”。上限9是额外票上限，在基础1票时最多10票；它限制个人权重，但不保证具体中奖百分比、绝对公平或中奖概率只上升某个固定数。多奖品、唯一中奖人规则继续按原快照算法，不给无法证明的概率数字。

直接加票活动继续展示真实每日/邀请规则及各自封顶/不限信息，不画人品闪电、不显示余额消费按钮。旧公告编辑仅作允许的投影调整，不变更冻结业务规则。

## 10. 数据与可靠性合同

以下是实施设计的最小实体建议，不是已存在的表或强制最终表名：

| 实体 | 最少保存的信息 | 约束 |
|---|---|---|
| 群人品规则 | 租户、稳定群、启停时间、规则revision、消息口径、单日30 | 全群统一获取参数；管理员不能暗中逐群改为不同日上限 |
| 人品账户及账本 | 群/用户、delta、类型、原始事实、业务键、发生时间 | 账本追加，余额缓存可重建，余额非负，账户唯一 |
| 人品消息与日进度 | 消息ID、用户、日期、内容指纹、接受/拒绝原因、日获取值 | 消息唯一、事务并发日上限；不保存无必要的聊天正文 |
| 活动兑换规则 | 模式、每人票上限、全部成本群及成本、revision、退款条款 | 发布冻结，与公告/私聊投影同源 |
| 兑换单 | 用户、活动、数量、逐群成本快照、消费账本关联、票账关联 | 业务键唯一，票源显式区别人品兑换，成本0也有兑换记录 |
| 调整/退款审计 | 操作者、目标、原因、前后值、来源、原兑换关联 | 不原地改余额或删除原记录；退款一次且可对账 |

积分不能存进 `UserGroupMessageTotal`，也不能把 `DailyProgress` 当永久余额；`TicketLedger` 仍是活动票事实，增加显式人品兑换来源。积分账户跨活动，兑换单与每场票账关联，而开奖只消费该场既有冻结票账与资格事实。

消息处理继续数据库先行Inbox；规则/积分/票账/通知按既有事务边界幂等。账户与日计数并发锁及唯一键覆盖重复、乱序、同秒、跨场消费；获取日计数不因消费回退。消息权限异常、账本不一致、余额无法重建、退款失败必须可见并阻止不可靠消费，不能静默返回0。
