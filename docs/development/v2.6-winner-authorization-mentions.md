# V2.6 中奖指定授权与身份提及修复

2026-09-05，用户明确要求：指定中奖人的权限只授予数据库或配置文件中写入的用户；前台中奖人必须 @ 展示，并检查相关细节。

## 授权合同

- `OPS_ADMIN_IDS` 配置名单，或 `winner_designation_operators` 中 `user_id` 匹配且 `enabled=true` 的记录，二者任一可授权。均使用正整数 Telegram 用户 ID。
- 活动创建者、群主、群管理员、普通 ADMIN_IDS 和参与者身份不自动获得指定权限。没有名单时无人获权，不存在自动授予第一个用户的逻辑。
- 查看活动、读取指定、设置、替换和撤销均执行鉴权。服务的每次操作在自己的数据库事务内重新检查；不能通过绕过 Bot/CLI 直接调用服务获得权限。
- 数据库名单的删除/禁用在下一次操作生效；进行中的操作持有授权行共享锁直至事务结束。配置名单修改需要重新加载进程配置。
- 迁移只建表，不自动写入任何获权用户。名单仅通过服务器配置或数据库维护，前台没有授权或指定入口。
- Bot 从真实 message.from_user 取操作人，且仅接受真人私聊；CLI 依赖服务器登录权限，--actor 是白名单校验与审计身份，不能提供给普通用户作为网络接口。
- 设置与撤销记录操作人、原对象、新对象、Bot/CLI 来源及本次授权来源（config/database）。既有资格、奖项名额、唯一中奖、开奖状态和行锁合同保留。

数据库维护形态（由服务器管理员执行参数化语句）：按 user_id 插入授权记录；将 enabled 改为 false 或删除记录可撤销数据库授权。如果该用户仍在配置名单中，配置授权仍有效。数据库授权错误必须显式报错，不能降级为默认允许。

## 前台提及与通知

- 中奖群公告和已开奖活动卡，用户名存在时展示 `@username`；没有用户名时展示可点击的 `@显示名`。两种均使用绑定原中奖 Telegram user_id 的 text mention，不依赖可能转让或改名的用户名解析。
- 标题、奖品、用户名、姓名、领奖说明统一 HTML 转义；不允许用户内容伪造标签或链接。不得把没有用户名的人改成原始数字 ID 展示。
- 中奖私信始终保留领奖方式和可点击发奖联系人，即使关闭扩展提示；扩展提示不决定必要领奖事实是否展示。
- “消息提示”提供可见的显示扩展说明/精简说明开关，标记当前选择，预览显示已保存状态。清理报名命令和提示保留时长为独立选项。
- 长中奖名单按 Telegram 消息实体解析后的 UTF-16 长度分页，每页独立 Outbox 与确认回执，禁止一次 Gateway 多次发送造成部分成功后重发。
- 有封面的已开奖卡遵守 1024 单位图注容量；摘要展示完整提及，容量不足时明确指向完整群公告。摘要按中奖名额计数，不能将同一人多奖误说成多个人。
- 不改写历史开奖或重发历史结果；发布后的新开奖使用修复后的消息。已完成历史消息仍保留原始事实。
- 发布切换期间尚未发送的旧格式中奖通知，在进入 Gateway 前按真实 Winner→DrawRun→Campaign 读取冻结发奖人；必须同时匹配原中奖者与收件人，不改原 Outbox 内容/哈希，也不猜联系人或放过不匹配记录。
- 本轮真实创建器发现旧模板时间误导：载入上次配置不复用上场具体开奖时间，定时抽奖明确要求设置本场时间；预览与发布共用输入校验，过期时间或不足结算窗口不显示“可以发布”。

依据：[Telegram 官方 Bot API 的格式与提及说明](https://core.telegram.org/bots/api#formatting-options)、[sendMessage 限制](https://core.telegram.org/bots/api#sendmessage)。

## 验证矩阵

1. 空名单、未获权的创建者/参与者、授权撤销、假操作人、群内调用全部拒绝；配置名单和数据库名单分别成功；直接服务调用不能绕过；拒绝不改变指定或审计。
2. 授权设置、替换、撤销有可追踪审计，数据库撤销后同一服务实例立即拒绝；已有指定最终仍走真实资格核验。
3. 有/无用户名、同名、特殊字符、Emoji、改名身份绑定；公告和文字/封面卡、领奖联系人一致。
4. 多页名单不漏人、不重复、每页符合实际长度、分页键独立且重新执行不开第二次奖；关闭扩展提示仍能联系发奖人。
5. 定向测试、迁移升级/降级与 drift 检查、全量分片、正常 CI 与 release、运行 SHA 与独立健康检查。
6. 复用自有无实物测试群和账号，检查未授权拒绝、授权指定、群内可点击提及与本人通知，记录 Telegram 真实实体和 message_id。
